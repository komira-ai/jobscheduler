Runs a CI step as a job: fetches its commit, runs its commands, brings back its outputs, and exits with its status. The job runs /bin/sh with a script that fetches the one commit of --source-url, runs --run with bash in the checkout, and then writes the paths of --outputs that exist to its stdout as a tar archive. js submits it (as js job run does: a lost answer is sent again with the same id), writes its stdout and stderr as they come, with the archive taken out of stdout and unpacked into --outputs-dir, and waits for its end; the first SIGINT, SIGTERM or SIGHUP cancels the job and waits, a second ends js. The job names no CPU or memory: the scheduler sizes it from the history of --step, or of --size-fallback while the step has fewer than five runs.

Usage: js ci run [OPTIONS] --os <OS> --image <REF> --step <NAME> --run <SCRIPT> --source-url <URL> --source-commit <SHA>

Options:
      --server <URL>
          The server, such as `https://jobs.example:7300`. Plain `http://` is accepted for a loopback host only: the bearer token never crosses a network in clear. Required

      --token-file <PATH>
          A file holding the bearer token: a regular file owned by you, mode 0600 or 0400. Required

      --ca-cert <PATH>
          A PEM file with the certificate to trust for `https://` (the server's, or the authority that issued it); only those certificates are trusted then. Optional: without it an `https://` server is verified against the public roots bundled in the binary, never the platform's store, because the places it is found can be redirected by the environment

      --json
          Print machine output (one JSON object per line) instead of text; errors too

      --os <OS>
          The machine the step runs on: macos (Apple silicon, natively under sandbox-exec) or linux (in a container)

          Possible values:
          - macos: macOS on Apple silicon, natively under a sandbox-exec profile
          - linux: Linux, in a container

      --image <REF>
          The image, pinned by digest (NAME@sha256:HEX): on Linux the container's, which must hold sh, mktemp, git, bash and tar; on macOS the bundle the job is named by

      --step <NAME>
          The step's name, which its size class is made of, such as `owner/repo/workflow/job`: every run of one name reads and teaches one history of what the step used

      --size-fallback <NAME>
          The class whose history sizes the step while its own has fewer than five runs. Default: the step's kind, ci-macos or ci-linux

      --run <SCRIPT>
          The step's commands, run as GitHub runs a `run:` step (bash -e -o pipefail) in the checkout

      --source-url <URL>
          The repository the job fetches its source from: an `https://` URL with no user or password

      --source-commit <SHA>
          The commit the job checks out: its full id, 40 or 64 lower-case hex digits

      --source-token-file <PATH>
          A file holding a token the fetch authenticates with (as the user x-access-token), for a repository that is not public: a regular file owned by you, mode 0600 or 0400. It reaches the job as a job file, which no read of the job returns

      --outputs <PATHS>
          The step's outputs: paths relative to the checkout, one per line. Each that the step made is brought back into --outputs-dir, whether or not the step succeeded

      --outputs-dir <DIR>
          The directory the outputs are unpacked into, made when missing

      --wall-limit <DURATION>
          The most the step may run, such as 90s, 15m or 2h
          
          [default: 1h]

      --network <LEVEL>
          What the job may reach over the network: none, allow-list or open. The fetch needs the repository

          Possible values:
          - none:       Nothing: the job cannot fetch its source, so only for a source the host holds
          - allow-list: The endpoints the host's operator allows
          - open:       Any address but the host's own and link-local ones
          
          [default: open]

      --env <KEY=VALUE>
          A variable of the step's environment, KEY=VALUE; may be repeated. Not for secrets: every read of the job returns its environment

      --id <ID>
          The job's id: 1 to 63 bytes of letters, digits, dot, underscore and dash. Not given: js draws one and prints it on stderr before it submits

      --github-output <FILE>
          A file to append the step's outputs for GitHub Actions to, `job-id=`, `outcome=` and `exit-code=` lines: the file `$GITHUB_OUTPUT` names

  -h, --help
          Print help (see a summary with '-h')

Exit status:
  0             the job succeeded, and its declared outputs were unpacked
  1 to 255      the job's step exited with this code (outcome failed); a job that failed without an exit code of its own, stopped for its memory, is 10
  11            the job was cancelled
  12            the job timed out: it was stopped at its wall limit
  13            the job was lost: its container is gone and no result exists
  14            the job failed to start
  15            how the job ended could not be told: a call failed, or the job is in a state this js does not know
  16            the job succeeded, but its declared outputs could not be read back
  1, 3, 4, 9    the submit failed, as for js job submit; with 9 the job may exist, and the same command with the same --id is safe to run again
  129, 130, 143 a second SIGHUP, SIGINT or SIGTERM ended js before the job ended; the job may still be running
  2             a flag is wrong
A step's own exit code can equal one of js's statuses; the outcome js prints (and writes to --github-output) tells them apart.
