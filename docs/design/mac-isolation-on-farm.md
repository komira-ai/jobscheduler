# The isolation test on a farm Mac, through the job service

Status: not built. A plan, for the step after the one that built the release's run of the test.

Every release runs the two-run isolation test of the Mac slot accounts (`crates/js-agent/tests/native_isolation`) as root on a hosted Apple silicon runner (`.github/workflows/js-agent-native-isolation.yml`, called by `release.yml` as `beta-macos-isolation`). It reports the verdict and holds back no archive, because on a hosted runner it cannot pass. Its verdict there is FAIL: the POSIX named semaphore run A made survives, and run B opens it by its name (the job profile allows `sem_open`, and macOS lists no semaphore names, so no reset can remove one: [mac-lease-teardown.md](mac-lease-teardown.md)). Its minimum set is not met either: launchd refuses the launch agent of `user/<uid>` to the job and to root with `Bootstrap failed: 5: Input/output error`, the uid having no login session there, and error 5 is not the proof of no path ([mac-lease-teardown.md](mac-lease-teardown.md), "The isolation test's `no-path` verdict"). The gate belongs on one of our own Macs running js-agent, whose pool accounts (`kbf-acct-<n>`) the agent's own pool makes. When the test passes there, `promote-macos` needs it, as it needs the other beta jobs.

## What it would take, in order

0. *The semaphore row.* Moving the test does not change what a named semaphore does: on a farm Mac too, run B would open the semaphore run A left, and the verdict would be FAIL. Before this route can pass, the row needs a decision: either the profile denies creating named semaphores (and Python's `multiprocessing` locks fail in a native job), or the test counts a surviving named semaphore as the accepted row the design already names.
1. *What it proves.* The test today builds the agent's pool and runtime in its own process, as root. Run through the job service, it would test the agent that is deployed: two ordinary native jobs, A that seeds and B that looks, on the same uid, with the agent's own retirement between them.
2. *The same uid for A and B.* `JobSpec` has no host, pool or slot field (`crates/js-proto/proto/jobscheduler/v1/job.proto`). The agent picks the uid: the first free slot after the one given last (`crates/js-agent/src/mac_accounts/mod.rs`). Either add a host or slot constraint to the job API (an additive field, scheduler and placer support), or keep a host whose `--native-account-range` holds one uid in a pool of its own.
3. *The seed and look program.* A native job runs a bundle (`@bundle/<entrypoint>`) or a program under the agent's tool roots, so the child role of the test becomes a digest-pinned bundle. A prints its uid and its tokens on stdout; the client passes them to B in `spec.env` or `spec.args`; B prints what it found. A client cannot declare outputs, so stdout (`js job follow`, `GetLogs`) carries the result.
4. *The root-side views.* A job cannot run `ipcs`, `ps`, `launchctl print` and `find -uid` as root. The agent's retirement proof (`crates/js-agent/src/mac_accounts/proof.rs`) already checks the processes, the System V objects, the home, `/var/folders` and the swept shared places of the uid once the account is gone. But it reports a pass only in the agent's log and a failure only as the host's taint (`cleanup-failed`). A per-job record of that proof that a client can read is needed. The post-job leak scan is not wired on Macs (`NoChecks`, `crates/js-agent/src/platform/macos.rs`).
5. *The launch agent.* Pool accounts have no login session, as on the hosted runner, so whether `user/<uid>` accepts a bootstrap there is to be measured on the Mac before this route is taken; until then the same error 5 may stop it.
6. *The CI path.* The farm CI reaches today is the build farm (`.github/workflows/macos-farm.yml`, [mac-farm.md](../mac-farm.md)), not the job service; no workflow submits a job. A release job would need the job service's address, a token for `js --token-file` from the release's secrets, and a network path to it (the build farm's tailnet route is the model), then submit A, wait, submit B and judge B's output. Like the other beta jobs it would gate only `promote-macos`.
