# Placement by measured and predicted load

Companion to [placement.md](placement.md) (6.3, where memory does not gate admission) and [sizing.md](sizing.md). This document replaces the
CPU and memory admission rule for actions; devices, whole-node reservation and the lease kinds are untouched.

## Problem
Admission counts booked CPU: every action books one core whatever threads it runs, so a node takes about as many actions as it has cores
(`Worker::has_room`, `free().fits(resources.without_memory())`), and memory is never summed. Measured mean parallelism per action is 1.4 to 2.1
cores. The 5 to 10 times is the run queue, not the cores per action: about 25 concurrent leases, each in a thread pool of about 89 threads, put
5 to 10 times as many runnable threads as cores on a node. Memory is protected only by the per-lease cgroup limit and the pressure backstop. The goal
is nodes at about 100% of CPU and RAM and never planned above it: the target is 1.0x of capacity, because past it threads queue and context-switch and every build on the node slows. Load-based placement is the placement, on by default, not an opt-in mode.

## Utilization
The goal is nodes at about 100% of CPU and RAM. Admitting to 100% of the predicted cost does not measure 100%: a prediction is the P90 of per-run mean cores, and a typical run sits below its key's P90. Model, not measurement
(there is no per-run distribution on the farm yet): if the per-run mean of one key is lognormal with median / P90 = 0.75 (`sigma = 0.2245`), then at the minutes where the predicted curve is held at 100% of `C` the measured CPU is
about `E[k] = 0.77 C` on average, where `k` is actual over predicted. The percentile of the CPU fit is a setting, `--placement-cpu-percentile`, shipped at 90 (memory always takes the maximum, for safety) and tuned later from the measured per-run distribution; under the same model:

| CPU fit | prediction / median | expected measured CPU at 100% predicted | model p99 of `k` | fault bound with `r = 2`, `f = 0.75`, no CPU slack, at the model's p99 `k` (88 threads / 16) |
|---|---|---|---|---|
| P90 (shipped) | 1.33 | 0.77 C | 1.26 | 320 cores = 3.6 C / 62 cores = 3.9 C |
| P75 | 1.16 | 0.88 C | 1.45 | 364 cores = 4.1 C / 70 cores = 4.4 C |
| P50 | 1.00 | 1.03 C | 1.69 | 421 cores = 4.8 C / 80 cores = 5.0 C |

The 0.77 and 0.88 figures are for predicted load held at 100% of `C`, which is the most admission plans. Estimator noise from a small ring (a key with 3 to 10 runs has a noisy P90 or P75) is not modelled. P75 would raise expected utilization by 0.11 C (14%) at the binding minutes with a model p99 `k` of 1.45, inside the target of 2; P50 would put the mean at the cap, with half the leases above their charge. The shipped percentile is 90, and moving it is a tuning step from measurements, not a design question. The fault bound at the targets (`k <= 2`) is unchanged by the percentile (see The overshoot bound); the column above is the same formula evaluated at the model's `k`, so it shows how much of that headroom a choice uses, not a forecast. The assumed spread is exactly what the
`k` histogram measures: if the real median / P90 is 0.9, P90 already gives 0.92 C and P75 buys little; if it is 0.6, P75 buys more and `k` rises further. A feedback correction that scales all predictions by the observed mean `k` was
considered and not proposed: under CPU saturation the measured per-lease use is capped by the node, so the observed `k` falls exactly when the node is full, and a correction built on it would admit more as the node saturates. If it is ever added it must use only windows below 90% measured CPU and be bounded to `[0.9, 1]`.

## Decision
There is no pinning, no cpuset and no QoS tier: a container may use any core. Admit an action when the node's measured load, plus the predicted
cost of what the measurement does not yet cover, plus the predicted cost of the new lease, stays within the node's capacity, for CPU and memory
separately. Per-node measurements come from cgroups each heartbeat; per-action-key costs are learned; the memory kill-and-retry ladder is unchanged. Capacity is the limit: the predicate never plans a node past 1.0x of `C_cpu` or `C_mem`, there is no slack above it, and load placement is on by default, with no shadow mode.

The flat rule (Signals, Learned cost, Admission, the overshoot bound, Starvation) is self-contained and complete without profiles. The Time profiles section is a layer on top of it:
it changes how a lease's cost is expressed (a curve instead of a number) and how the predicate is evaluated (at each future minute), and every case it does not cover falls back to the flat
rule. Read the document in that order.

## Which placer this changes
**js-sched is the implementation.** The predicate, the cost record, the sums, the score and the starvation reservation are written once, in `js-sched` (`Worker::has_room`, which today
checks `free().fits(resources.without_memory())`, memory only against capacity, and the lease cap), as a pure module `load.rs` with shared test vectors. kbf reaches the same module through
kbf-sched, a pure `pub use js_sched::*` re-export with no copy of `load.rs` or anything else; the rule is written once. The kbf work is plumbing only: the node reader (`node_load.rs`), the `NodeLoad` heartbeat field, the
`Runtime` method and the flags.

What stays as it is, because it is a different admission scope and neither reads a measurement:
- `js-registry` `Runs::admit` (the `/runs` interim API) sums the declared `limits.cpu_millis` and `memory_bytes` of a lease's live runs against the lease shape. It is a per-lease budget *inside* an already
  placed lease, not a host placer; it is unchanged by `--placement-load`.
- `js-pool-static` books a whole host to one lease. It is unchanged.
One host belongs to exactly one placer, so the two cannot disagree about it: a host the lease-table path books is never evaluated by the load predicate.

**Relation to `--placement`.** Load placement is the default under `--placement sched`. With `--placement lease-table` it does not apply and the setting resolves to `off`; an explicit `--placement-load on` with `--placement lease-table` is refused at start-up (not ignored), and the flag golden of the lease-server lists it.

## The cost record in js-sched
Each admitted lease carries, in `Worker`'s per-lease map, a `LeaseCost { p_millis, m_bytes, limit_bytes, rung, curves, started_mono }`: the predicted CPU cost, the predicted memory cost, the cgroup limit and the ladder rung as
separate fields (the request's `Resources.memory_bytes` stays the cgroup limit, as `has_room` already treats it, so nothing that reads it changes), the profile curves used at admission (at most 64 buckets of two
`u32`, 512 bytes; empty for a flat lease), the agent-reported start that defines `covered`, and `key_hash: u64` (for the same-key share in the score): FNV-1a 64 over the class bytes, a `0xff` separator byte, then the dedup bytes (offset basis `0xcbf29ce484222325`, prime `0x100000001b3`). The covered and uncovered sets are derived from `NodeLoad.covered` and `started_mono` and are not stored. `Event::Heartbeat` gains
`load: Option<NodeLoad>`. **The cost is persisted with the lease** (in the lease record that replay reads) and is the value used after a restart: a recovered lease is never re-estimated from the current estimator, so the sums
before and after a restart agree. This is data in the pure crate; the estimator is never read inside the scheduler's decision, only at admission by the caller that produces the cost. The store does not yet persist the cost, so until it does a lease recovered through the store is charged its request (jobscheduler#96).

## Signals
Additive and optional; an old agent omits them, an old server ignores them.

| Field | Meaning |
|---|---|
| `cpu_usage_usec` | cumulative `usage_usec` of the actions cgroup (`cpu.stat`); descendants removed since are still included |
| `mono_usec` | the agent's monotonic clock at the same read; the only time base used for windows (the scheduler's injected `FarmTime` is used only for freshness; production never reads wall time, as the pure scheduler does not) |
| `memory_working_set_bytes`, `memory_active_file_bytes` | `memory.current` minus `inactive_file` from `memory.stat` of the actions cgroup (floored at 0), and `active_file`. The server uses `ws = working_set - max(0, active_file - a * C_mem)`: the file-page part is capped at the share `a` of the node's memory (default 0.25, `--placement-ws-file-share`), so retained hot page cache can never make an idle node read as full. Without the cap an idle node whose leases have ended keeps their pages active until reclaim, which only happens under memory pressure, so `working_set >= C_mem` would refuse every action and no pressure would ever reclaim. At most `a * C_mem` of cache counts; anon, shmem and kernel memory always count in full. A worker with no action lease counts a working set of 0 (stricter than the cap: an idle node can never read as full). Chosen over anon plus kernel because it keeps shmem and tmpfs outputs, which are not reclaimable; it still counts hot (active) file pages, which errs toward under-admitting, never toward a kill. Cold page cache, the bulk of a busy node's cache, is excluded. |
| `covered` | the leases that were running for the whole window since the previous reading (by the agent's own start, so a start held back by the pressure backstop or an image pull is not covered) |
| `actions_cpu_limited` | whether the actions cgroup has a `cpu.max` other than `max`, read from the cgroup; a worker in an `on` pool that reports `true` is admitted by the fallback (below) and counted, so a node that was not restarted with the flag is safe, not silently wrong |
| `cpu_throttled_usec`, `cpu_pressure_some_total_usec` (cumulative; a rate is taken over the same window as the CPU) | telemetry only; never feed admission |

Server side, per worker: a measurement is accepted for any `seq` larger than the last accepted one within one daemon process (`mono_usec` did not go back); else it
is dropped, and a dropped reading needs two new accepted readings before the worker leaves the fallback. `measured_cpu` = `delta usage / delta mono` in millicores, integer; admission and
scoring use the larger of the last two windows (a rise is believed at once, a fall after two windows). Values that fail `validate` (implied cores above
4x the capacity in cores, memory above 4x capacity, counter going back) count as absent. All arithmetic is integer, saturating or `u128`. A signal older
than three windows is stale. `W` is the heartbeat interval the welcome sets (5 s by default).

## Learned cost per action key
Both costs are the existing `js-sizing` estimate (`Estimate::cpu_millis`, `memory_bytes`), with these changes:

- **P90** is nearest-rank over the samples that exist: sort ascending (ties by ring slot, oldest first), take rank `ceil(0.9 n)` (1-indexed), so one to four samples give the maximum. The ring is ordered oldest-first and a new
  sample overwrites the oldest slot. The same definition is used everywhere the document says P90 (cost, profile minutes), and the shared vectors of `load.rs` include tiny rings, ties and a full ring.
- **CPU:** `round_up_250m(Pq(cpu_usage / wall))` with `q` from `--placement-cpu-percentile` (default 90; "P90" below means this percentile; see Utilization) over the 32-sample ring, whole-run means, clamped to `[floor, node threads]`. Today a cold key
  (no usable summary: `Fallback::Cold`, `Missing`, `Stale`) has no estimate and the caller books a default; with 1 to 4 samples the figure is the P90 of
  the samples that exist (`Summary::cpu` does not check `N_MIN`).
- **Cold cost:** CPU `cold_cpu`, default 2 cores (measured mean parallelism is 1.4 to 2.1); memory 4 GiB (`Bounds::default_memory`, the first rung).
- **Memory** is `1.2 x max + 128 MiB` rounded to 256 MiB (not a peak; the estimator tabulates its own misses), at least 1 GiB. A retry up the ladder is
  admitted at `max(learned, the rung it was killed at)`, so a spiky key killed at 4 GiB is not counted at its learned 2 GiB again.
- Cost is clamped to capacity, so a node-wide key runs on an otherwise idle node.
- **Sub-core costs.** `CPU_MIN_MILLIS` goes from 1000 to 250 (one 250 m step). A 0.3-core action then costs 0.5 core, not 1, and a node can hold
  `C / 0.5` such leases (at most the lease cap and the memory term). Keeping 1000 would make short light actions, which finish inside the
  in-flight phase, cost exactly what they cost today.
- **Heterogeneous nodes.** Each sample also records the thread count of the node it ran on (one `u16` per ring slot, 64 bytes per key). A sample that
  used at least half its node is a pool-sized action and is scaled by `target threads / sample threads`; a narrower sample is not scaled. The cost is
  the P90 of the scaled samples, clamped to the target. `C_cpu` is hardware threads, so "100%" means threads busy; no SMT normalisation.
- **Learning under load.** Today a CPU sample is kept only below 100 permille node CPU pressure, which a node at 100% load rarely meets, and an unknown
  pressure (Mac, no PSI) drops it. New rule: a sample taken at or above that pressure, or with none, is kept **only if it exceeds the key's current CPU
  estimate**. A starved run understates its demand, so a kept value is never above the truth: the estimate can only rise under load and falls on the
  quiet runs and the existing staleness. The "current estimate" of a key with no estimate is its cold cost (2 cores): such a key is learned under load
  only from a run that used more than 2 cores. The ratchet is therefore one-way while a node is saturated: an overestimated or cold key never falls
  there, because the lower samples are the ones dropped. That errs toward under-filling (the key is counted above its truth), never toward
  overload; it corrects on the first quiet run, and the observation target on mean measured CPU and the count of keys with no CPU sample
  would show it if it persisted. Counted per key and farm-wide: samples kept, dropped under pressure, and keys with no CPU sample.

## Admission
This section is the flat form of the predicate: it is what a cold key, a key demoted by the shape guard, a retry, and a worker in fallback are charged. By default the cost of a key with enough runs is a curve over its lifetime and the predicate is checked at every future minute (Time profiles below); both forms have the same shape.

For a worker with capacity `C` (CPU threads minus reserve; memory after floors), each lease `i` has the cost `(p_i, m_i)` fixed at admission and held
until its result (any outcome: end, kill, requeue). `U` is the set of admitted leases not in the latest accepted `covered` (uncovered), at most about
`2W` after the agent starts them. VM leases are outside the actions cgroup: their booked CPU and memory, `V`, are added to every sum.

    CPU:     max( measured_cpu, f * sum(p_i, covered) ) + sum(p_i, uncovered) + V_cpu + p_new  <=  C_cpu
    memory:  max( sum(m_i, all), ws + sum(m_i, uncovered) ) + V_mem + m_new  <=  C_mem * (1 + s_mem)

There is no CPU slack: `C_cpu` is the limit, and admission never plans past it. `s_mem = 0.00` likewise. Memory is the maximum of the measured working set and the sum of the predicted costs of every running lease,
held to the lease's end; **predicted memory never decays**, so a lease that allocates late is still counted at its prediction. CPU decays to the
measurement only down to a floor: the covered leases are charged at least `f` times the sum of their predicted cores (default `f = 0.75`, flag
`--placement-cpu-floor`; a constant-duty key is floored at `f_c = 1`, below), and the measurement can only raise the figure above it. Without the floor a covered lease in an idle phase (fetching inputs,
waiting) measures about 0, so each window would refill the whole headroom while earlier leases sleep, and several batches could wake together. `f`
is set from the cost model: a prediction is the P90 of per-run mean cores, a typical run sits near three quarters of it, so at `f = 0.75` the floor
does not bind for leases in their normal phase and measured load keeps its job of correcting under-predictions and releasing the headroom of
over-predicted keys; only the idle-prelude case is held. A smaller `f` admits more and loosens the bound by `1/f`; `f = 1` makes the CPU side the pure
predicted sum raised by the measurement (the fallback figure). The histogram of `k` shows where `f` can sit. The sums are updated after each placement, so one
round cannot place more than the headroom. `request.memory <= capacity.memory` and the lease cap stay. Whole-host, whole-machine and exclusive leases keep
their rules.

**Constant-duty keys.** A saturated node's measurement stops at `C`: the cgroup cannot report more CPU than the node has. For constant-duty actions, whose measured use is their prediction, a floor below 1 would let admission plan past `C` while the measurement reads 100%, and the excess would show only as a longer run queue (at `f = 0.75` the covered demand could reach `1 / f = 1.33 C`). So a key whose fitted curve stays within one 250 m step of its flat cost at every minute, with no idle phase for the floor to hold headroom for, is floored at `f_c = 1` (`--placement-cpu-floor-constant`, default 1000 permille) instead of `f`: its covered leases are charged at least their full prediction, and their admitted demand `P_c` is at most `C`. Other keys keep `f`, which exists for the idle prelude; the bound for varying work (below) covers them.

**Fallback.** A worker with a stale, absent, dropped or implausible signal, no cgroup (Macs with `MacFootprint`, native and VM nodes, cgroup v1), or an old

**Memory guard.** Memory is never planned over RAM. In addition to the profile predicate, a worker admits a memory-profile lease only if `sum(flat memory cost b_i over every running lease, including cold and demoted leases) + V_mem + b_new <= (1 + d) * C_mem`, with `d = 0` (`--placement-flat-memory-slack`, on by default). It is evaluated in the same pass as the profile predicate and both must pass, the flat sum using the persisted cost record's flat field, not the curve. It never applies to a whole-host, whole-machine or exclusive lease, which keep their own rules and are not blocked by it. Each lease is limited to `1.5 b_i + 512 MiB`, at most `1.63 b_i` for `b_i >= 4 GiB` and at most `2 b_i` for `b_i >= 1 GiB`, so physical use is at most about `1.63 (1 + d) C_mem` for leases booked at 4 GiB or more and `2 (1 + d) C_mem` in the worst small-booking case, which with `d = 0` is `1.63 C_mem` and `2 C_mem`. With `d = 0` the flat sum is the memory admission limit, so memory profiles no longer pack beyond the flat rule; they stay on for the telemetry, and a later non-zero `d` is a tuning step from data. This is the lead's reading of the target for memory, to be confirmed: the same 1.0x as CPU, because swapping slows builds as context switching does, so memory is never planned over RAM.
daemon, is admitted by the same predicate with the measured side dropped and each lease charged once: CPU `sum(p_i, all) + V_cpu + p_new <= C_cpu`, with the sum over all the worker's leases, covered and uncovered alike (the uncovered term is not added again), and memory `sum(m_i, all) + V_mem + m_new <= C_mem * (1 + s_mem)` with the working set omitted: the sum of the predicted costs of its leases, no decay. The cost floor in the fallback stays 1000 m for a worker with no measurement at all (Mac, native, VM): nothing there measures a light population, so only predictions protect it. It never falls back to booked-only. Such a worker is as safe as its predictions are good, and the cold cap below limits the rest.

## The overshoot bound
**Expected behaviour.** Inference from the model, to be checked against the alarms; the fault bound is further down.
- *Peak.* Planned load never exceeds `C` at any slot the predicate charges, whatever the score does, because the predicate refuses it. Measured CPU over `C` on a node comes only from predictions that are too low (`k` above 1) and peaks above a lease's mean (`r`); the share of windows over `C` is reported. There is no 10% margin to spend: key 1 of the score is that refusal, so a host is never chosen for having room in a slack zone.
- *Constant-duty work* is floored at `f_c = 1`, so it is admitted up to `C` and no further (see Admission): a saturated node's measurement stops at `C`, and the floor, not the measurement, is what keeps the planned demand at `C`. Its run queue is the thing the `cpu.pressure` telemetry shows.
- *Mean utilization* is below 100% at full prediction (see Utilization): about 0.77 `C` at P90 and 0.88 `C` at P75 under the model. The predicate does not fix this: at `tau = 0` the measurement replaces the prediction for covered leases, but at every later slot only the curves count. The levers, in the order of their effect: the CPU percentile and the floors `f` and `g` (a lower floor releases idle-prelude headroom at a cost of `1/f` in the fault bound). Scoring does not raise the mean by itself; it makes the hosts that are full full at the right minutes. The mean of `k` per node, already an alarm, says how far from 100% the pool is, and the percentile is tuned from it.
- *Correlated misses* are the realistic way to see measured CPU well over `C`. Leases of one key started by one build fan-out have the same `k`, start-aligned curves and the same peak minute, so no independence argument applies to them (nor to a node-wide lease, `n = 1`). Key 4 of the score limits one key to a quarter of a host's `C_cpu` while another host that is equal on keys 1 to 3 is available: at `k = r = 2` one key then demands at most `r k x 0.25 = 1.0 C` of a node, and at a 4x miss (sim i, `k = 4`) `2 x 4 x 0.25 = 2.0 C`. When every host in the pool is at the share, or the pool is one host, the limit does not apply.

**Acceptance**, in the alarm style of the rollout table (an alarm, not a gate), one set of numbers used everywhere in this document:
- The target is not to plan above 1.0x: no admission whose predicted load exceeds `C` at any slot the predicate charges (a count that must stay zero, including on flat-charged and fallback workers). Measured CPU / `C` is reported (p99, p99.9, and the share of windows over `C`) and read as feedback on the predictions, not as a threshold: the first measurements decide the next lever.
- Mean measured CPU / `C` above its pre-deploy level (the goal of the design), and the mean of `k` weighted by `p_i` times time at least `f`.
- The share of placements decided by key 3 (distrusted host chosen), by key 4 (concentrated host chosen), and the hosts kept empty (host-minutes with no lease, on hosts that rejected nothing). Reported.

Sim x asserts, on a replay of the farm trace through five rankers with synthetic per-minute curves from the ground-truth model (sims a, h, p): p99 ground-truth CPU / `C` per node not above the old rule's, and no admission planned past `C`; mean fill at least the old rule's; queue wait p95 not worse; memory kills not above the old rule's. These are assertions on the mechanism with the model's independent misses, not a gate on `on` and not evidence of the real gain.

**Derivation.**
Let `M` be the CPU of covered leases at the last reading, `P_c = sum(p_i, covered)`, `U_w` and `U_c` the predicted cost of uncovered warm and cold
leases, so `max(M, f P_c) + U_w + U_c <= C`. Let `k` be the **whole-run mean** cores over predicted cores of a warm lease (`mean cores / p_i`, the figure the histogram below records; the mean is learned,
so `k` includes the lease's own variation between runs), `r` the factor by which a lease's peak window exceeds its whole-run mean (`peak window / mean`, also histogrammed), so a lease's demand in one window is at most `r k p_i`; `A` the CPU a
cold lease can use, and `n_c` the cold leases uncovered at once. The covered leases demand at most `r M` when the measurement is the larger term, and at
most `r k P_c` when the floor is (any covered lease, idle now, can wake to its peak window); with `f P_c <= C` the second is at most
`r k C / f`. Then the demand in any window after admission is

    P_cpu  <=  (r k / f) * C  +  n_c * A

(the uncovered warm term `r k U_w` is inside it, since `f P_c + U_w <= C` and `f <= 1`; `r M` is inside it too, since `r k / f >= r` once `k >= f`, and below that the floor is the larger term). The floor is what makes this a bound: stated
without it, the covered term `r M` is about 0 when covered leases are idle and the covered leases are bounded by nothing but the admission history.

Cold cap: at most `cold_per_window` leases with a cold CPU cost are admitted per worker per window, default `ceil(C_cpu / 32)` (setting
`--placement-cold-per-window`); a lease stays uncovered for at most `2W`, so `n_c = 2 * cold_per_window`.

**Cold ramp.** The cap limits how fast unlearned keys enter. On an idle 88-thread node (`cold_per_window = 3`, `W = 5 s`, cold cost 2 cores) cold admission proceeds in steps of `cold_per_window` per window for as long as the node has room. The number of cold leases that fit is not fixed at `C / 2 = 44`: the measurement already contains the CPU of the uncovered leases, which the predicate charges again at their prediction, so room runs out earlier, by an amount that depends on how much the cold leases actually use. A backlog of unlearned keys drains at no more than 36 starts a minute per node; a mass-cold event (a toolchain bump, a cleared estimator) with a thousand distinct keys therefore takes about half an hour on one node and proportionally less on a pool, and only for actions shorter than the ramp (longer ones fill the node anyway). Each key is cold once, after its first run it has a figure. To drain a mass-cold event faster an operator raises `--placement-cold-per-window` for the pool and restarts the scheduler with it;
the bound moves with it by `n_c * A` (at 12 per window: `n_c = 24`, so `469 + 96 = 565 cores = 6.4 C` on 88 threads at `f = 0.75`, against 493 = 5.6 C at the default) and sim o asserts the bound with the new `n_c`.

Defaults (`f = 0.75` for a key not known to be constant-duty, `f_c = 1` for a constant-duty key, no CPU slack), with the observation targets below (`k <= 2`, `r <= 2` at p99, `A <= 4` cores at p99), so `r k / f = 5.33` and `r k / f_c = 4`:
on 88 threads `n_c = 6`, so for `f = 0.75` `P_cpu <= 5.33 * 88 + 6 * 4 = 469 + 24 = 493 cores = 5.6 C`, and for `f = 1` `P_cpu <= 4 * 88 + 24 = 352 + 24 = 376 cores = 4.3 C`; on 16 threads `n_c = 2`, `P_cpu <= 5.33 * 16 + 8 = 85 + 8 = 93 cores = 5.8 C` for `f = 0.75` and `4 * 16 + 8 = 72 cores = 4.5 C` for `f = 1`. (With `f = 0.5`: `r k / f = 8`, 728 cores = 8.3 C and 136 cores = 8.5 C, which is why the range stops at 0.5 and the default is higher.) At most about 5.6 C, not 10 times. It is a worst case at the p99 criteria, not the expected overshoot; CPU is compressible, so it slows work and does
not fail it. The bound lasts until the leases admitted at `r k` times their cost finish, which can be minutes to hours: the next heartbeat shows the rise
and stops further admission, and a key with understated cost relearns by the rule above, but that protects later leases only. A lease is uncovered for
`2W` plus the heartbeat delivery delay.

**Fault bound.** `P_cpu <= (r k / f) C + n_c A`, about 5.6 C on 88 threads at `f = 0.75` (5.33 C from the first term, 0.27 C from the cold leases) and 5.8 C on 16 threads; for constant-duty keys (`f_c = 1`) 4.3 C and 4.5 C. This is what the arithmetic allows if, in the same minute, every covered lease on one node is mispredicted 2x (`k = 2`) and peaks 2x over its own mean (`r = 2`), after the leases sat idle at the 0.75 floor the instant before, so that admission believed the node nearly empty. It takes every lease at its p99 `k` at once, perfectly correlated, which is a conservative ceiling and not the p99 of the node total. It is a ceiling at stated targets, not a forecast, and it is exactly the case the scheduler cannot see in advance because it learns of the rise at the next heartbeat. It is bounded at the p99 targets (`k <= 2`, `r <= 2`, `A <= 4`); beyond them only the alarm protects. About 1% of leases are above the targets by definition and there is no CPU limit (no `cpu.max`), so the hard ceiling of the system is the number of leases times the node's thread count, not 5.6 C. The independence argument holds for leases of unrelated keys and fails for a same-key fan-out and for a few node-wide leases. CPU is compressible, so exceeding the bound slows work and does not fail it, the next heartbeat shows the rise and stops further admission, and the overrunning leases finish. Scoring does not change the bound, because every host it ranks has already passed the predicate; key 4 changes how likely a correlated miss is to hit one host.

**What lowers the fault bound.** `f`, at a cost in packing (`f = 1`: 376 cores = 4.3 C on 88 threads; `f = 0.5`: 8.3 C). The CPU slack is already zero, so there is nothing further to take from it. `cold_per_window` lowers the `n_c A` term only. A pool of only profile leases is bounded by 3.3 C at the targets (see "The bound with profiles"). The cost of `f = 1` is the idle-prelude headroom that `f = 0.75` releases; the histogram of `k` shows how much that is.

Memory: a lease cannot exceed its cgroup limit `1.5 x booking + 512 MiB`, so a cold lease (4 GiB) has `k_m <= 1.63` and
`P_mem <= (1 + s_mem) * C_mem * max(1, k_m)`; a warm key's miss is the estimator's tail (target `k_m <= 1.3` at p99). The per-lease limit and the node
backstop kill beyond that, as today. What bounds `k` is not the mechanism but its measured value, hence the histograms below and the alarmed targets.
Persisting above `C` needs leases whose real use exceeds their prediction, and the learning rule raises those predictions.

## Time profiles
The rule above charges each lease one number for its whole life. Many actions are not flat: a fetch phase, then a burst, then an upload. Two actions whose
busy minutes do not overlap can share a node that two flat peaks cannot. With profiles on, a lease's cost is a curve over minutes since its start, and admission
checks the node's predicted load at every future minute within a horizon, not only the peak. Profiles are the scheduling basis for CPU and memory from the first deploy, with an operator off switch only: `--placement-profile on|off` and
`--placement-profile-memory on|off`, both default `on`. The per-minute series is always collected, whichever the switches say, so history exists before it is used; with a switch `off` the
flat rule above applies to that resource. A key with fewer than 3 usable runs is charged flat until it has runs. Observation (the histograms) never gates use.

**1. Sampling.** The daemon already reads each running lease's cgroup every `W` (for `r`). It now bins those reads by minutes since the lease's own start
(the agent's clock, the same actual start `covered` uses, so an image pull or a held start does not shift the curve): per closed minute, the mean cores (`delta cpu.stat usage_usec / delta mono`), the peak single-window
cores, and the maximum working set (`memory.current` minus `inactive_file` of the lease cgroup). The minutes are read while the lease runs, not only at its end.
They reach the server in the heartbeat: `NodeLoad.minutes` (field 10) and `repeated LeaseClock { LeaseId lease = 1; uint64 started_mono_usec = 2; }` (`lease_clocks`, field 9, the agent's start of each running lease; the server's elapsed minutes `e_i` are `(latest accepted mono_usec - started_mono_usec) / 60 s`, rounded down, and 0 for a lease not yet reported), `repeated LeaseMinute { LeaseId lease = 1; uint32 minute = 2; uint32 cpu_mean_millis = 3;
uint32 cpu_peak_window_millis = 4; uint64 ws_max_bytes = 5; }` (about 24 bytes). At most one record per running lease per minute, and at most 64 records
in one heartbeat, oldest minute first and then by lease id: twelve heartbeats a minute carry 768 records, above the lease count of a node, so a healthy node never
queues. After an outage the daemon keeps unsent minutes for 10 minutes and drains them 64 a heartbeat (256 leases for 10 minutes is 2,560 records, 40 heartbeats or 3.3 minutes if nothing new arrived; the 256 new records a minute leave a net 43 a heartbeat, so about 5 minutes to catch up); older minutes
are dropped and counted (`minutes_dropped`), and a run missing more than a fifth of its minutes does not enter the ring. A record is idempotent by `(lease, minute)`, so a resend after a
reconnect is harmless. The final partial minute of a lease rides on its result.
Per node, nothing new is sent: the server derives the node's per-minute series from the cumulative `cpu_usage_usec` and the working set already in `NodeLoad`.

**2. Retention.** In the scheduler's state store, two tables, both numbers only:
- `key_profile`, per action key (by `key_hash`, per platform class): a ring of the last 32 runs' per-minute series (cores and working set, up to
  64 minutes a run; bucket 63 is the maximum of the per-minute means from minute 63 on, conservative), and the fitted profile. Only runs that ended on their own enter the ring: a run killed
by the memory ladder or the pressure backstop, cancelled or requeued is truncated and would bias the curve low, so it is excluded from the CPU column (the ladder's rerun enters). The one exception, in the memory column only, is a kill at the lease's own cgroup limit (below); cancelled, requeued and node-backstop-killed runs are excluded from both columns. At most about 25 KB for a key with long runs, a few hundred bytes for
  a key whose runs last a minute or two. The whole table is bounded by `--profile-store-bytes` (default 256 MiB), evicting the least recently used key (an evicted key is charged flat until it is relearned), and ages
  with the same staleness rule as the cost estimate. A row is written when a run ends, not per minute.
- `node_minute`, per node: minute, mean cores, working-set maximum, lease count; kept 14 days (14 x 1440 rows of 32 bytes, about 0.65 MB per node), pruned daily. It is telemetry, never an admission input: the server buffers a node's rows and writes them in one batch every 5 minutes, so a scheduler crash loses at most 5 minutes of it.
Per-lease raw minutes are not kept outside the ring. Apart from that 32-byte minute ring in the summary, nothing else is stored: no argument vector, path, environment, user or output, only the `key_hash`, the node
identifier the scheduler already holds, and counts. The telemetry tables are public-safe by construction.

**Profile shape: absolute minutes since start, not normalised to run length.** Admission aligns a running lease by its elapsed time and does not know when it
will end; a normalised curve would need a run-length forecast, and where run lengths vary a normalised curve smears the busy phase across the run. In absolute
minutes the variation in run length simply shows as the spread of runs reaching each minute. The fit, per minute `t`: the P90 across the ring's runs that reached `t`
of mean cores, and the MAX across them of working set (with the memory margin of the flat rule, `1.2 x max + 128 MiB`; see Memory safety for why memory takes the maximum). Under node pressure the flat rule's keep-if-higher applies per minute: a
minute from a run taken at or above 100 permille CPU pressure, or with none, enters the fit only where it exceeds the current fit at that minute (the key's flat cost for a key
with no curve), else it counts as missing, so a starved run cannot flatten the curve. The values are then **dilated** by `delta = 2` minutes (each value is the
maximum of the fitted values within `t +- delta`) so a busy phase that starts a little early or late is still covered. Dilation costs co-admissions: two busy phases are co-admitted only with an idle gap of at least `2 delta = 4` minutes between them (a busy phase ending at minute 2 dilates to 4, so the first busy phase admitted beside it starts at minute 7), and the telemetry counts the verdicts that `delta = 0` would have admitted and `delta = 2` refused (`profile_dilation_missed`). A minute reached by fewer than a quarter of the
runs holds the previous value (the tail); a lease that outlives the curve is charged the tail. A run under a minute is one bucket, which is the flat cost.
`p_bar` below is the key's flat cost (the P90 of whole-run means, as above).

**3. Use in admission.** A lease's charge at minute `t` since its start is `c_i(t) = max(curve_i(t), g * p_bar_i)`, with `g = f = 0.75`
(`--placement-profile-floor`, range 0.5 to `f`; lowering it is a later decision from the histograms): the profile can lower a lease's charge in its idle minutes, never below `g` times its flat cost. Cold keys, keys
with fewer than 3 usable runs, keys demoted by the shape guard, and every worker in fallback have no curve: they are charged flat (`p_bar` and the floor `f`),
exactly as before: a covered flat lease is charged `f * p_bar` and an uncovered one `p_bar`, and a profile lease is floored at the same `g * p_bar` with `g = f`, so mixed sums are consistent. For a candidate worker, with `e_i` the elapsed minutes of each running lease and `H` the horizon (default 30 minutes), admit when for every
`tau` in `0..H`, and once more at `tau = H+` (below):

    CPU:     F_tau + sum(c_i(e_i + tau), uncovered) + V_cpu + c_new(tau)  <=  C_cpu,    F_0 = max(M, sum(c_i(e_i), covered)), F_tau = sum(c_i(e_i + tau), covered)
    CPU, H+: every lease charged its remaining maximum of c_i from minute e_i + H on (the tail included), summed with V_cpu and the new lease's remaining maximum  <=  C_cpu
    memory:  max( sum(R_i(tau), all), working_set_0 + sum(R_i(tau), uncovered) ) + V_mem + R_new(tau)  <=  C_mem * (1 + s_mem)

At `tau = 0` the measurement still enters (it can only raise the figure); at later minutes only the curves do. An uncovered lease (the in-flight rule) is
charged the maximum of its curve over its first two minutes, so a lease that has just started is never counted at its quiet start. `R_i(tau)` is the
**remaining maximum** of lease `i`'s memory curve from minute `e_i + tau` on, including the tail, and never less than its current working set: memory is held until the
lease's peak is behind it, then released, never before. Cold and flat leases hold their cost to the end as before, and a lease retried up the ladder is charged flat at its rung.

**Expected life.** The charge of a lease that has not started ends at its expected life: for a key with a learned wall time, the P90 of its wall minutes plus `delta`. From that minute on the new lease adds nothing to the sums, and the `H+` check does not charge it, so an action that lasts under a minute is not refused for a peak that arrives after it is gone. It is on by default. A lease with no wall-time history keeps the whole-horizon charge. A lease that runs past its expected life, about one run in ten, enters the sums through the measurement at the next heartbeat, not through its charge. Only the candidate's charge ends; a running lease is removed at its result, as before. It is an admission change in the pass that holds the predicate, not a scoring change.

**Memory safety is the ladder.** Memory is not compressible and the remaining maximum drops the flat rule's guarantee that predicted memory never decays: after its curve's peak a lease that
allocates again is charged only its working set. What bounds it is the kill-and-retry ladder, unchanged: the booking and the lease's cgroup limit (`1.5 x booking + 512 MiB`) stay at the flat cost, so a lease
whose memory runs past its curve rises to the limit and is killed individually, then retried at the next rung, charged flat at that rung. The key learns from it: the killed run does not enter the CPU
ring (its CPU curve is truncated and would bias low). Only a kill at the lease's **own cgroup limit** enters the **memory** column, as a *censored* run: its per-minute working set up to the kill counts as observed, and the kill
minute and every later minute up to the 64-minute cap count at `memory.peak` at the kill (a lower bound on the true peak). Cancelled, requeued and node-backstop-killed runs enter neither column. The retry, if it ends on its own,
enters both. **The memory fit is the MAX across the ring's runs per minute** (times the flat rule's margin, `1.2 x max + 128 MiB`, then dilated), not the P90, and the CPU fit stays the P90. The reason: memory is not compressible, a P90 curve
is exceeded by about one run in ten by construction, which would make the 0.1% misfit target and the demotion trigger inconsistent with the fit, and with a 32-run ring and nearest-rank P90 one high sample does not move the curve at all. With MAX a
single kill raises the curve at once, from the kill minute on, to the observed peak, and it stays until the run leaves the ring (32 runs) or the staleness rule retires it. A curve value is capped at the key's flat cost, which the same censored
peak also raises. **Memory misfit** is a lease-minute whose working set exceeds its remaining maximum `R_i`, or a kill by the cgroup limit; it is counted per key and fleet-wide. The automatic per-key fallback is
the shape guard, for CPU and memory alike: a resource's curve is demoted to the flat hold for the next 8 runs when 2 of the last 3 runs, **or 3 of the last 10 runs**, misfit (the second trigger catches a misfit every third run, which 2 of 3 never does). Stated precisely, per trigger: misfits clustered within 3 runs cause at most two kills before the demotion (2 of 3); misfits spread every third run cause three kills within 10 runs, the third trips the demotion (3 of 10); misfits spaced 5 or more runs apart trip neither trigger and are not demoted, each costing one kill. In every case each kill raises the curve (the MAX fit), so a repeat needs new growth. After a demotion the key is charged flat for 8 runs, and it can then be killed again, once per cycle.

**Memory worst case.** In the window before a misfit lease is killed the node holds the sum of curves exceeded by that lease's excess: `P_mem <= (1 + s_mem) C_mem + sum over misfit leases (L_i - R_i)`, where `L_i`
is the lease's cgroup limit and `R_i` its charge; with `s_mem = 0` and a flat-cost booking `b_i`, each misfit lease adds at most `1.5 b_i + 512 MiB - R_i` (an example, not a maximum: a warm key booked at 4 GiB with a 1 GiB tail charge adds `1.5 x 4 + 0.5 - 1 = 5.5 GiB`; a 32 GiB booking with a 2 GiB tail adds `48 + 0.5 - 2 = 46.5 GiB`, about 46 GiB). The number of simultaneous misfits is what the bound depends on, and is not capped by a formula: misfits are rare per key (the fleet target is at most 0.1% of lease-minutes, and each key is kicked to flat after two), but a
shared cause (a changed input that makes many keys grow late together) can misfit many at once. Their excess is then removed by the per-lease kill or the node pressure backstop, as today, and the number of retries per
lease is at most the rungs of the ladder. The worst case is therefore a bounded excess per misfit lease for the time to the kill, not a sustained sum. The new memory rule is stricter than today even in this worst case, since today memory is not summed at all and a lease is limited only by its own cgroup. The node backstop remains a safety net, not a demonstrated bound: this document does not claim that it holds the node under a correlated misfit, and sim u asserts what it does.
**The bound with profiles.** Define `k_c` as the lease-minute's actual mean cores over its charge `c_i(t)` (histogrammed per lease-minute; a minute counts only when the actual exceeds
the charge by at least 250 m, so a tiny charge cannot dominate) and `q` as the peak window of that minute over the minute's mean. A profile lease's demand in a window is at most `q k_c c_i`; a flat lease's is at most
`r k p_bar_i` with a charge of at least `f p_bar_i` (the bound above). The sum of the charges is within `C` at every minute, so

    P_cpu  <=  max( r k / f , q k_c ) * C  +  n_c * A

With the targets (`r, k <= 2` at p99, `q <= 2`, `k_c <= 1.5` at p99, `A <= 4`) and `g = f = 0.75`: the flat term is 5.33 and the profile term 3, so the figures are those of the flat rule,
**493 cores = 5.6 C on 88 threads and 93 cores = 5.8 C on 16**; a pool whose demand is only profile leases is bounded by `3 * 88 + 24 = 288 cores = 3.3 C` (`3 * 16 + 8 = 56` cores = 3.5 C on 16).
The CPU worst case with profiles on at the defaults (`g = f = 0.75`) is the figure above, 5.6 C on 88 threads and 5.8 C on 16. CPU is compressible, so exceeding it slows work and does not fail it, and the demand is transient (the next heartbeat
shows the rise and stops admission; the overrunning leases finish). The profile term is a statement at the targets, not a hard cap: a profile that is wrong (a busy phase where the curve said idle) has a large `k_c` for its minutes, and the hard limit there is only the floor,
`r_b k / g` with `r_b` the key's own peak ratio (3 to 4 for a bursty key), about 8 to 11 for one lease type, before the guard acts. That is why the shape guard and the alarmed target exist and why sim q
asserts a wrong profile. The **shape guard** (per key): 2 of the last 3 runs, or 3 of the last 10, with a minute at `k_c > 2.0` demote the key (the same two triggers as for memory misfit) to the flat cost for its next 8 runs, counted. It is looser than the fleet target (`k_c <= 1.5` at p99), which
is a statement about the whole population, so that a single noisy minute does not demote a key. Lowering `g` below `f` (admitting more at a larger worst case, `r k / g`) is a later decision from the histograms
and not part of shipping; the off switch keeps the flat rule one setting away.

## Starvation
A host marked for a whole-node request (reserved or draining for a whole-machine, exclusive or VM lease) is excluded **before** the load predicate and before scoring: its load falls as it drains, which would otherwise let the predicate pass it for work that refills it, so the whole-node request would miss its deadline. The existing mark is the gate; the predicate never sees such a host.

No tiers; queue order is kept. A **pool** is the set of workers a request can run on (platform, drivers, devices, avoid set), as `Servable` computes it.
The **head** is the first queued action, whole-machine, exclusive and VM requests excluded (they keep the existing whole-node reservation, and a worker
that holds one is never chosen), that has no worker with room. It reserves the worker in its pool with the smallest binding ratio
`max((L_cpu + p) / C_cpu, (L_mem + m) / C_mem)` (`L` the left side of the predicate without the new cost), sticky while that ratio is within 0.1 of the best. This is what the implementation does. A refinement was considered and is not implemented: reserve the worker where the head first passes the predicate over the horizon (the smallest `tau`), because best fit keeps the emptiest-now host light and that host may hold a long lease with a late peak. A reserved worker admits no later request (a request that fits elsewhere goes elsewhere; one that fits only there waits, as for a whole-node
reservation). One reservation per pool: a second blocked head waits until the first starts, then becomes the head. A reservation on a worker whose
signal goes stale stays and uses the fallback figures. Bound: the head starts within the longest remaining lease at reservation, plus `2W`, plus one
round. Work ahead of the head is never held back.

## Lying or stuck node, restart
- **Plausibility.** Lease CPU arrives only when a result does, so a long lease would lag any comparison (its hours of CPU would land in one short
  span). The check therefore uses only leases that were admitted and ended inside the span, and compares their summed `cpu_usage_us` with the growth of
  `cpu_usage_usec` over the same span (which also holds the other leases, so the growth can only exceed the sum on a healthy node). The span
  extends back window by window until the sum reaches 60 core-seconds, at most one hour; below that the check is *unchecked*, not failed, and the
  unchecked time is reported. Growth below half the sum marks the signal implausible, and the worker uses the fallback until it agrees again;
  a node with no lease reporting more than half of `C_cpu` for three windows is marked the same way. This catches a wrong cgroup, a stuck counter and a
  broken reader on any node with turnover; a node running only leases longer than the span is unchecked and says so, and an agent that lies in both
  places is out of scope.
- **Scheduler restart or new leader.** Recovered leases count their persisted cost (never recomputed from the current estimator) as uncovered; the first heartbeat
  after re-registration has no previous reading, so the worker is in fallback for it and measured from the second (about `2W`). After a restart every worker reads as never-measured until its next accepted reading, so recovered leases are charged at the 1000 m fallback floor until the second heartbeat. Never booked-only.
- **Lease end** removes its cost at the result; a short action therefore costs its prediction for its whole life, which is why the sub-core floor matters.

## Scoring
The predicate decides whether a host may take the lease. The score decides which of the hosts that pass. The predicate is not changed, so scoring cannot admit anything the predicate refuses and cannot move the fault bound.

**Level.** Scoring ranks the workers a consumer holds, inside a lease (level 2 of two-level leasing, design.md 9.1; the level of kbf-sched and `Worker::has_room`). It does not rank hosts for bookings at level 1 and does not touch `FirstFit`, the pool's packing onto the fewest machines, or the scaler's `scale_down_util` (a booked share over the pool, level 1). If load-ranked admission is ever applied at level 1 in a scaling pool it must keep "new work goes to the first fitting host so the others go idle"; curve best fit is not applied at level 1 for now. Doing so would also mean reading the `scale_down_util` booked share on the predicate's horizon instead of `tau = 0`, because best fit leaves hosts full at some future minute and about half full now; that belongs to a pool-scaling design. This section changes nothing in the pool-scaling design.

**Order of exclusion.** Per request: (1) hosts outside the pool (platform, drivers, devices, avoid set); (2) hosts marked for a whole-node request, retire, reclaim or evict, dropped before the predicate and never scored; (3) the head reservation, as in Starvation; (4) the predicate, including the cold cap, the lease cap and the `H+` check; (5) the score, over the hosts left. One host left: it is taken and nothing is scored. Whole-host, whole-machine, exclusive and VM leases keep their rules and bypass scoring; a worker the request would own whole (a whole-host, whole-machine or exclusive placement) keeps the previous rule and is not scored.

**Goal.** Put the lease where its per-minute curve fits the host's predicted curve most tightly, so hosts run near 100% of CPU and memory and, where the pool allows it, other hosts stay empty. Two leases whose busy minutes do not overlap should end up on the same host. "Fullest now" does not do that, because it ignores shape. The score compares the new lease's curve with each candidate's predicted load curve minute by minute (an overlay over the horizon) and squares the leftover: a lease goes where it leaves the least unused capacity at the minutes that matter.

**Inputs.** All of them are computed by the predicate pass. For host `h` and each slot `tau` of the predicate (`0..H`, and the `H+` slot):
- `Lc(tau)`, `Lm(tau)`: the left sides of the CPU and memory predicates without the new lease (millicores, bytes).
- `Nc(tau)`, `Nm(tau)`: the new lease's charge exactly as the predicate charges it: the curve (`c_new(tau)`, `R_new(tau)`) for a key with a curve, and for a flat-charged lease (cold key, fewer than 3 usable runs, demoted key, retry, fallback) the flat charge `p_bar` and its flat memory at every slot. The same 3-run threshold as the predicate; the score has no threshold of its own.
- `Tc = C_cpu` and `Tm = C_mem`, the predicate's limits.

**Scored minutes.**
- *Safety (key 1, the predicate's refusal, and key 2) looks at every slot the predicate charges*: `tau` in `0..H` and the `H+` slot. A flat lease is charged flat across all 31 minutes, so a cold lease cannot be placed on a host that would be over 100% at minute 10 by looking only at minute 0.
- *The fit (key 5) looks at the lease's own life*: `tau` in `0..L-1`. `L` is the number of leading minutes `t` (0-indexed) that at least half of the key's ring runs reached, clamped to `1..H`; a flat-charged lease and a key whose runs are under a minute have `L = 1`. In production today `fit_minutes` is 1 (the flat load provider); `L` comes from `life_minutes` once the profile admission layer supplies it. The minutes after `L` and the `H+` slot are not in the fit: the curve holds its tail to the lease's result, so thirty tail slots would outweigh two busy ones and the fit would become "mean level". `js-sizing` exports one `u8`, `life_minutes` (= `L`), per key. The existing ring holds no wall time, so the per-key summary keeps a 32-byte per-run minute ring for `L` (stored format version 2; version-1 records decode with `L = 1`).

**Residuals**, in parts per million of the host's own capacity, so a 16-thread and an 88-thread host compare directly. Products in `u128`, results `u64`, floor division; the signed `dc` and `dm` are `i128` and, for every host that reaches the score, not negative, and `xc`, `xm` are at most `10^6` in `u64`. The key 5 sum is `u64`: it is at most `max(2, b) x 10^12` per slot times the sum of the weights (`2 + ... + 31 = 495`), about `2.0 x 10^15` at `b = 4` (`3.7 x 10^15` even with every weight at 31), far below `1.8 x 10^19`.
- `dc = Tc - Lc - Nc` (signed). `xc = max(0, dc) * 10^6 / Tc`. A host with `dc < 0` at any slot has been refused by the predicate and is not scored.
- `dm = Tm - Lm - Nm`. `xm = max(0, dm) * 10^6 / Tm`. With `s_mem = 0` a host with `dm < 0` has been refused by the predicate and is not scored.

**Keys.** Lower is better, compared in this order. `w(tau) = H + 1 - tau` for `tau` in `0..H` (31 down to 1) and `w = 1` for the `H+` slot; in key 5 the largest scored `tau` is `L-1 <= H-1`, so `w` runs from 31 down to 2. Near minutes are certain, far minutes are noisy, and a valley at minute 25 will be filled by arrivals before then.
1. `refused`: not a score term. A host with a slot over 100% of `C_cpu` or `C_mem` does not pass the predicate, so no host that reaches the score has a slack zone to order. The number stays so that keys 2 to 5 keep theirs. The aim is 100% and never over.
2. `memory_unsafe`: 0 if, at every predicate slot, `Lm + ceil(kappa_m * Nm) <= Tm`, else 1. `kappa_m` is 13/10 for a warm key (including a key demoted to flat, which still has runs) and 163/100 for a cold key and for a retry up the ladder (the memory targets `k_m`). An ordering and never a refusal. CPU has no such key: CPU overshoot slows work, memory overshoot kills it. This key sits above the fit on purpose: in a mass-cold event on a memory-bound pool it spreads cold 4 GiB leases over every host that still has room for a 1.63x miss before it packs any of them. It trades packing for fewer kills; sims o and z assert it.
3. `distrusted`: 1 if the host is in fallback (no measurement, Mac, native, VM node, stale signal) or if its measured covered CPU exceeds the predicted sum of its covered leases (`M > P_c`: the predictions are known to be too low there), else 0. Best fit prefers the fuller-looking host, and a fallback host with no decay looks fuller than a measured one with the same leases; without this key the host with the least information would be packed hardest. The predicate still protects it with the sum of predictions.
4. `concentrated`: 1 if the host's covered and uncovered leases of the same key plus the new lease's `p_bar` exceed `--placement-key-share` of `C_cpu` (default 25%), else 0. Best fit by itself concentrates identical curves on one host, and one key has one `k`: a 2x miss on a fan-out of a single key is perfectly correlated. An ordering and never a refusal: when every host is above the share, key 5 decides. The share is 25% of each host's own `C_cpu`, so on a 16-thread host a lease above 4 cores is always "concentrated"; this cannot starve it, because the key only orders and never refuses.
5. `fit = sum over L-scored tau of w * ( 2 * min(xc,xm)^2 + b * (max(xc,xm) - min(xc,xm))^2 )`, with `b` the integer `--placement-score-balance` (0 to 4, default 1). `min(xc,xm)` is the leftover of the binding resource, squared: best fit. The difference is the leftover of the other resource that nothing can use (stranded), counted at `b/2` of the binding term. `b = 1` is a judgment, not a measurement. The range stops at 4 so that stranding can at most double the binding term (`b/2 = 2`). The expanded form `sum R^2 - 2 sum R N + sum N^2` (the cross term is the dot product of demand and headroom; `sum R^2` pulls towards fuller hosts) is exact for one resource only; the min/max split is not expanded.

**Tie-breaks**, in order, when keys 1 to 5 are equal; pure and deterministic.
1. Fewer uncovered leases (its numbers are less likely to move at the next heartbeat).
2. The larger `C_cpu`, so the smallest host takes the fewest new leases and is the natural retire or swap victim.
3. The larger minimum over the next 5 minutes of `Tc - Lc`.
4. The smaller 64-bit FNV-1a hash (offset basis `0xcbf29ce484222325`, prime `0x100000001b3`, bytes in the order below) of `len(lease id) as u32 LE, lease id, len(worker id) as u32 LE, worker id` (length-prefixed, so `(ab, c)` and `(a, bc)` differ). Equal scores spread by lease, not by host order. The hash is fixed (not a seeded std hasher) and the encoding is pinned by the shared golden vectors. The lease id is hashed in its root text form `term-seq`, and the worker id as its text.

Lease count is not a tie-break: under best fit it would pull towards spread. It stays a feasibility cap only.

**Example.** Two 88-thread hosts, limit 88 cores. Host A runs 60 cores in minutes 0 to 2 and 10 after; B runs a flat 24. Curves are relative to now and the busy phases are already dilated by `delta = 2` (A's 0 to 2 is 60 cores through minute 4). The new lease has `p_bar` = 32 cores, so its quiet charge is the floor `0.75 x 32 = 24` cores, and it is busy at 60 cores in raw minutes 7 to 13 (dilated 5 to 15). Predicate: A is 60 + 24 = 84 at minutes 0 to 4 and 10 + 60 = 70 at minutes 5 to 15; B is 48, then 84. Both pass (at most 88). Key 5 picks A: A's leftover is 45,454 ppm at minutes 0 to 4 and 204,545 ppm at minutes 5 to 13, B's is 454,545 ppm and 45,454 (floor division), and the near minutes carry the larger weights. The old rule looked at load now (A 60/88 = 68.2%, B 24/88 = 27.3%) and chose B, which leaves 40 cores free in the near minutes. The discrimination of the refusal (key 1) from key 5 is sim z.

**Cold keys and demoted keys.** No curve: the charge is flat at every slot (cold: 2 cores, 4 GiB), `L = 1`, the fit is the residual now and keys 1 and 2 look at every slot. The cold cap is an admission rule and is unchanged. Flat and profile leases mix without a case: flat leases enter `Lc`, `Lm` through their flat charge, the same sums the predicate builds.

**Cost per round.** Per request and feasible host, one pass over `H + 2 = 32` slots and 2 resources is 64 evaluations, the same pass as the predicate, each with one `u128` division, so at most 64 per request and host. Nothing here is measured. Scoring runs inside the pass that holds the scheduler lock, so it lengthens the hold time; this design does not claim to add none. A burst of 1,000 queued requests on 6 hosts is 384,000 evaluations and at most about 0.38 million `u128` divisions; at an assumed 20 to 50 ns each that is 8 to 19 milliseconds under the lock, to be measured in sim x (reported, not asserted: no wall-clock test) and reduced if it matters (`u64` arithmetic suffices below 16 TiB of memory per host, since `16 TiB x 10^6` is below `2^64`). The vectors `Lc`, `Lm` (32 x 2 x 8 B = 512 B per host) are built once per round and updated after each placement by adding `Nc`, `Nm`; anything that changes a host's leases, moves `M` at a heartbeat, or ends a lease invalidates them. They are derived state, rebuilt from the persisted cost records on recovery. A counter inside the scorer records evaluations. A vector asserts equality: evaluations per round `== feasible_hosts x 64` per request, summed over requests, and zero for a host that failed the predicate or was marked, so a pass that runs twice, or a host scored after exclusion, turns it red.

**Where it lives.** In `load.rs` beside the predicate, pure integer (no `f64`), with shared vectors, and reached from kbf through kbf-sched's re-export of js-sched (kbf supplies only the node reading, the heartbeat field and the flags). Flags: `--placement-score-balance`, `--placement-key-share`. No environment variable, no pinning, no tier. A pure function for the previous least-loaded choice is kept only as the baseline in sim x.

**Unmeasured.** No per-minute profile exists on the farm yet: the saved action logs have whole-run wall time and mean parallelism per action, not per-minute series. The daemon starts collecting when this design ships. The gain from curves over flat best fit is therefore an assumption; sim x uses synthetic curves and can show the mechanism, never the real gain (sim x2 runs on the collected series). The weights `w`, `b` and the key share are judgments: fix them after x2, not before.

Where the overlay can act is limited by the dilation. Actions under a minute are scored flat. A 2 to 5 minute run dilated by `delta = 2` on each side is nearly flat and needs a 4-minute idle gap beside another busy phase, so the expected overlay gain on them is small. The gain, if any, is on actions longer than about 5 minutes. The mix (the count and the share of machine time by action length) is not known here: it is measured from the telemetry before the weights are tuned, and sim x reports it. Reducing `delta` for short keys is a later decision from `profile_dilation_missed`.

**Expected life, outside this section.** A running lease is removed at its result, so a 30-second action does not hold anything for 30 minutes. What would be charged for 30 minutes is a *candidate*: the predicate charges the new lease its curve (a flat lease its flat cost) at every `tau` in `0..H` against the other leases' future peaks. For an action under a minute that would refuse placements that are gone before the future peak arrives, and that costs utilization, which is the point of this design. Scoring cannot fix it, so the fix is the admission change described under Time profiles: the new lease's charge ends at its expected life (the P90 of wall minutes plus `delta`). Sim af quantifies the refusals it removes.

## Telemetry
Per worker each heartbeat: measured CPU and memory over capacity, uncovered cost, sum of predicted cost, throttled time, run-queue proxy
(`cpu.pressure`), non-action CPU, plausibility state. Per finished lease: histograms of `k` for CPU (`mean cores / p_i`, the same `k` as the bound), the share of node-windows where the floor binds (`f * P_c > M`),
of `r` (`peak window / mean`, from the daemon's per-heartbeat read of the lease cgroup) and of `k_m` (`memory.peak / m_i`). Per key: cost, sample count;
farm-wide: cold and unsampled keys, cold leases admitted; the histograms and counters `k_c`, `q`, `memory_misfit`, `shape_guard_demotions`, `minutes_dropped`, `profile_dilation_missed`, and the mean of `k` per node weighted by `p_i` times time; per worker p99 working set over `C_mem` and OOM events at the `actions/` cgroup; the placements decided by key 3, key 4 and by tie-break, hosts kept empty, and scorer evaluations. `C_cpu` is hardware threads: 100% means threads busy, not cores, so on SMT hardware a node at 100% is further from full than it reads. The summary reports the distribution of measured CPU over capacity, the share of windows
above `C`, and the run queue.

## Rollout
Load placement is on from the first deploy; it is the placement, not an opt-in mode, and there is no shadow mode. A hidden emergency off exists for rollback: `--placement-load off` (per cluster, or per pool with `--placement-load-off-pools`). It is not a supported mode, and nothing is tuned for it. The profile switches `--placement-profile off` and `--placement-profile-memory off` are operator switches. Profiles are used
from the first deploy; the per-minute series is collected from the first heartbeat, and a key has a curve after 3 usable runs (until then it is charged flat). The emergency switch is separate from the profile switches because it also changes what kbf-node writes (`cpu.max`, NUMA) and what admission trusts, and a way back must not depend on a redeploy: the Welcome carries the pool mode, so the node restores or removes `cpu.max` at its next reconnect without a restart.

The numbers below are observation targets with alarms, not gates: each is exported and an alarm fires when it is missed, and the operator's response is the off switch or a flag, not a blocked release.

## Decided
- **Load placement is the placement.** It is on by default under `--placement sched`. There is no shadow mode and no opt-in. A hidden emergency off exists for rollback; it is not a supported mode. The pool mode is carried by the Welcome so a node follows it at reconnect without a restart.
- **The target is 1.0x.** CPU has no slack: admission never plans a node past `C_cpu`, so there is no headroom above capacity and no slack zone in scoring. Key 1 of the score is the predicate's refusal of any slot over 1.0x and orders nothing. Constant-duty keys are floored at `f_c = 1` (1000 permille). There is no measured-CPU percentile target. The target is not to plan above 1.0x.
- **The fault bound is lower.** `P_cpu <= (r k / f) C + n_c A`. At the p99 targets (`r = 2`, `k = 2`, `A = 4` cores, `n_c = 6` on 88 threads and 2 on 16) with `f = 1`, constant-duty keys and any lease floored at 1: `4 * 88 + 24 = 376 cores = 4.3 C` on 88 threads and `4 * 16 + 8 = 72 cores = 4.5 C` on 16. With the idle-prelude floor `f = 0.75` for other keys: `5.33 * 88 + 24 = 493 cores = 5.6 C` and `93 cores = 5.8 C`. A pool of only profile leases at the targets: 3.3 C and 3.5 C. It assumes every covered lease on one node is mispredicted at the p99 target and peaks at once, after sitting idle at the floor, with the cold cap as stated; it is a ceiling at the stated targets, not a forecast, and CPU is compressible, so exceeding it slows work and does not fail it.
- **Memory is never planned over RAM.** The flat-sum guard is on with `d = 0` (`--placement-flat-memory-slack`). This is the lead's reading of the target for memory, to be confirmed.
- **A new lease's charge ends at its expected life** (the P90 of wall minutes plus `delta`). It is on by default.
- **No best fit at level 1 for now.** Scoring stays at level 2; `FirstFit` and the `scale_down_util` booked share are unchanged.
- **The CPU percentile is a setting.** It ships at 90 and is tuned from measurements; there is no feedback correction on predictions.

**Where the code differs.** The code does not yet use these defaults: `Scheduler::new` keeps the booked rule unless `with_load_config` is called, the configuration still has the `Shadow` and `Off` modes as ordinary values, the CPU slack default is above zero, there is one floor `f` for every key, key 1 of the scoring code still orders a slack zone with a tolerance flag, and the flat-sum guard and the expected-life end are off by default. A follow-up code change brings js-sched to these defaults, and the change to scoring key 1 is made in the scoring code.

## Out
Pinning, cpusets, NUMA placement, QoS tiers, per-action reservations, a CPU limit on the actions cgroup (for `on` pools), and any client environment
variable. The cgroup limit of a lease stays the memory ladder's.

## Order
The sampling and the tables come first in the order below, since a key has a curve only after 3 runs and history should accumulate from the first deploy.

`js-sched` first, with the follow-up that brings its defaults to the decided ones: `load.rs` (the predicate, the cost record, the score) with the shared vectors, the persisted cost, the simulations, and the `--placement-load` flag under `--placement sched`; with the `NodeLoad` fields in `js-agent-wire` and the `js-sizing` changes. Then the plumbing in kbf (`node_load.rs`, the `Runtime` method, the proto field, the daemon heartbeat, the node flags) and the same module through kbf-sched's re-export, with `cpu.max` and `numa-node` removed; and the `js-agent` collection slice from the team that maintains it.
