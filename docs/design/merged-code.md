# The merged code and what it becomes

> Status: a plan of the extraction steps, kept as history. The `Pool` port, `BoxedPool`, `FakePool`
> (`js-provider-fake`), `RegisteredProvider` and the lease table it names are deleted; `HostBook`,
> `Observed`, `ChooseOver`, `SeatError` and `StartAck` stay in `js-provider`, and `js-pool-static`
> stays as the static pool file without a `Pool` impl (D36).

Moved from design.md section 5.9. Section numbers refer to design.md.

| Merged item | Becomes | Follow-up |
|---|---|---|
| `js-provider::Provider` (`start`, `stop`, `observe`, `capacity`) | **Renamed `Pool`** (the scheduler's internal allocation port; `BoxedProvider` and `FakeProvider` are now `BoxedPool` and `FakePool`). Still to do: `ProviderId` to `PoolId` and `capacity()` to `hosts()`. The host-booking surface of a pool: book a free host for a lease, release it, observe it, and list its hosts (`hosts()`, D16). It is not a provider kind. | Rename PR (step 23) |
| `Flavour`, `flavour()`, the doc "delegated flavour only" | **Deleted**, and the doc rewritten. One kind of thing runs work; `CapacityProvider::can_launch` says whether a machine provider launches. | Done with the rename |
| `StartAck`, `StopAck`, `Observed`, `StartSpec::new` | Stay: cloud calls can time out, so the three answers stay. `AcquireAck` and `ReleaseAck` are added beside them; the fence and no-retries rules are still to model. | Step 23 |
| `HostCapacity` and `capacity()`; the `js-provider` crate | On `Pool`, `capacity()` is renamed `hosts()` (hosts and their leases). `CapacityProvider::list` (instances, with instance id and tags) is new, and the crate gains `CapacityProvider` beside `Pool`. | Step 23 |
| `StaticPool` (`js-pool-static`) | Stays, as the `static` capacity provider, **for tests only**: its listed hosts are a test fixture, and a production configuration declares none. It never launches. It is also the operator-listed pool behind today's `--pool-config` and the GPU lease service, a **stepping stone**: the GPU machines move to running `js-agent` and registering with a `default` provider, after which that file is retired. | Steps 28, 54 |
| `HostBook`, `Candidate`, `ChooseOver`, `Held`, `SeatError` (the booking table, now in `js-provider`) | Stay, in `js-provider`, beside `Pool`: the static pool and the registry of self-registered hosts both book through `HostBook`, so the table does not go with `js-pool-static` when that crate becomes a test fake. | Step 6 |
| `RegisteredProvider`, `Registry` (`js-registry`) | The host table is behind the `static` machine provider, `StaticCapacity` (a `CapacityProvider` that never launches; `acquire` answers `Refused(capacity)`), and `RegisteredProvider` still books leases on it through `Pool`. `RegisteredProvider` is the **core of the `DefaultProvider`**: hosts that register themselves, booked for a lease like any pool's. It gains the capable-host check, the `no-capable-host` refusal and `regain_grace` (providers.md), the `pool-full` refusal, and the kind name `default`. It creates and destroys nothing. | Step 30c |
| `LayeredProvider` (`js-lease-server`) | Today it asks its children in a **fixed order** (the static pool, then the registered hosts), moving on only when a child answers `NoCapacity`, `NoFit` or `UnsupportedClass`, and answers the most hopeful decline. That becomes the **configured hierarchy** of a pool: the order is the pool's `providers`, an elastic entry is asked to acquire only when no entry has a free capable host, and the "most hopeful decline" becomes the refusal rule (`NoCapacity` is a wait, an answer no host could ever give is `no-capable-host`). | Step 31c |
| `pool.seat()`, `Seated`, `Unseated` | Stay for the in-memory static pool. For aws, instance tags are the record, so seating becomes re-adoption by tag. | Step 32 |
| `CapacitySource` | The extension seam. Its one implementation for configured providers builds, from the kind registry of 5.7, a source over any `CapacityProvider`; `RegisteredAgentSource` serves the `default` provider's registered hosts. Its lock-held, synchronous call becomes asynchronous, because acquire is slow (D19). | Steps 29, 30, 32 |
| `js-provider-fake` | The merged fake becomes the fake capacity provider (fake aws), with scripted launch failure, slow boot, unknown acquire, unknown terminate, instance loss, leaked instances and quota refusal. | Step 28 |
| `js-conformance` | The machinery stays: `Subject`, `Check::ALL`, `Verdict::NotApplicable`. Its checks are re-keyed to the capacity-provider and agent contracts; wording about flavours goes. The labels-on-created-resources follow-up named in its crate doc lands with the first provider that creates resources. | Steps 28, 32 |
| `js-lease` | Stays. Adds an `acquiring` state before `pending`, `held` and `releasing`, the pool name in the lease file (additive), an acquire record, and the tainted-host set (5.12). | Steps 29, 30b |
| `js-lease-server` | Stays. `POST /v1/leases` accepts a class and label selectors (additive); a registration endpoint serves agent hello; a pool-scaler tick runs beside the reaper. | Steps 29 to 33 |
| `js-cli` | Gains `--pool`, `--class` and `--label` on `acquire`, and `host clear-taint`. | Steps 33, 30b |
| `js-agent-wire`: `Hello.capabilities` (string pairs, at most 64), `Shape`, `Phase`, `JobSpec.isolation`, the refusal constants | Stay. `Hello.facts`, `Heartbeat.facts_rev` and `facts`, `HeartbeatReply.facts_ack` and `exclusive`, `Heartbeat.exclusive_ready`, `JobSpec.runtime` and `vm` are added as optional fields, with new limits and refusal constants; protocol major 1 is unchanged. `Phase::Preparing` and `Restoring` serve the whole-node sequence; no phase is added. | Steps 37, 42, 46 |
| `js-types`: `Capabilities` (a string map), `Shape::satisfies`, `Dim` (no `vms`) | `Shape::satisfies` stays for the legacy map; the typed model and the constraint evaluator are the new `js-caps`; `Dim` gains `vms` (an unknown dimension is refused today). | Steps 36, 44 |
| `js-registry`, `js-lease-server` agent routes | Hold the newest facts snapshot per host (soft state), acknowledge revisions, match `needs` at the grant and record the matched revision and image in the lease (additive). | Steps 37, 39 |
| `js-agent` facts (`Platform`, the GPU probe, the bounded command runner) | Gain `os_version`, `xcode`, `sim.*` and VM-store probes and `--cap`, reusing the same runner. | Step 38 |
| `js-agent` lifecycle over `Runtime` (and the docker and podman backend in review) | `Runtime` is unchanged. The lifecycle reaches it through a `Sandbox` seam; `VmRuntime` is a second backend of the seam. `HeldState` gains nothing. | Steps 41 to 43 |
