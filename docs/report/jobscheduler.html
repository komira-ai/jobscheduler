A build farm, a benchmark rig and a CI system all need the same thing: run a piece of work on a machine that has room for it, on its own, and leave nothing behind that changes the next piece of work. jobscheduler is one scheduler service and one agent on each host. A client submits a job, an OCI image pinned by digest with its resource needs and a wall limit. The scheduler queues it, books an allocation on a host before it tells the host, and the agent runs it with crun on Linux or natively under a sandbox on macOS, then reports the result.

The problem. The first run is easy. The hard parts are a client that disappears, whole-host work that starves behind small jobs, hosts that go silent or reboot, jobs that must start fast and stay contained, Macs that have no container runtime with the isolation Linux has, and capacity that comes from owned machines and from clouds that charge by the hour (design: Problem).

The hypotheses.

  1. If the scheduler commits a job’s placement and its allocation before it tells the host, a crash between the two leaves a record that the next pass resolves, never a booking nobody knows about.
  2. If a host that is only silent frees nothing, and only a provider’s word that the host is absent does, the scheduler never runs a job twice on two hosts.
  3. If a job is the one public concept, bounded by a queue wait, a start timeout and a wall limit, a client that disappears leaves nothing that needs it to stay alive.
  4. If a whole-host job marks the host with the least estimated time left and lets small jobs in only when they end inside that time, whole-host work finishes behind a stream of small jobs.
  5. If the agent starts a job with crun directly, with no container daemon in the path, a job starts fast; on a Mac a pooled user, a generated sandbox profile and a checked teardown give it the isolation a container gives it on Linux.

The solution. One process, js-lease-server, serves a protobuf job service (jobscheduler.v1.JobService) over gRPC and an HTTP/JSON gateway, and places queued jobs with one placement engine, js-sched. Each host runs js-agent, which says hello, heartbeats, takes a start and a stop per job, and lists the jobs it holds and their results. Machines come from hosts that register themselves and from three cloud providers behind one CapacityProvider contract. The CLI and the client library are generated from the service definition.

Where it stands. jobscheduler is early, and in the middle of a change of model. The code on main serves two APIs from one process: the older lease API, where a client books a host and posts runs into it, and the newer job API, which is the design. The table says what is built; the design as built re-checks every status the design gives against the code, what is not built yet lists the gaps, and what we have measured says plainly that no performance number has been taken with the measurement harness yet.

Work on someone else’s machine: the problem

The design states six problems (design: Problem). Each is a way a naive scheduler, one that picks a free host and runs a command on it, goes wrong.

A client that disappears

A client submits work and stops answering. The work must still end, the host must come back, and the result must wait for the client. In a lease model, where the client holds a host and renews it, the host is held for as long as the client says so, and a client that dies holds it until a timer runs out. The design removes the client from the path that keeps work alive: a job is bounded by its own limits, not by its client.

Whole-host jobs starve behind small ones

A benchmark that needs a quiet machine never gets one while small work keeps arriving: each small job that ends frees room another small job takes. Draining a host costs the remaining time of the work on it, and that cost has to be chosen, not accidental.

A host is an unreliable thing

A host can go silent, reboot, be reimaged, or be compromised by the job it ran. A scheduler that frees a silent host’s bookings may start the same job on a second host while the first still runs it. The scheduler must say “unknown” when it does not know.

Jobs must start fast and be contained

A job is an image. Launching it should not wait on a container daemon, and it should write only where it is told and reach only the network it declares.

Macs are different

A Mac has no container runtime with the isolation Linux has. Isolation on a Mac is a user of the job’s own, lent from a pool and reset between jobs, a sandbox profile and a firewall rule, and the teardown has to be checked, not assumed.

Capacity comes from several places

Owned machines, machines rented by the hour and machines a cloud’s VM API starts are all capacity. A job should go to the first source that can serve it, and a machine that costs money needs hard caps and a brake, because a bug costs money.

What that leaves

From what the cited pages show: SkyPilot and dstack place work across clouds and Kubernetes; Kueue MultiKueue spreads jobs over Kubernetes clusters; Nomad schedules general workloads and its raw_exec driver runs on every system it supports, but without isolation; Orchard runs Mac virtual machines. None of those pages describes running an OCI image as a native, sandboxed process on a Mac host beside crun containers on Linux hosts under one scheduler, which is the gap jobscheduler is built for. That is a statement about the pages read, not proof that no such system exists.

Where another system is the better choice

From the same pages: for many clouds and Kubernetes clusters at once, SkyPilot covers far more providers than the three jobscheduler has. For Mac virtual machines on Apple Silicon, Orchard is built for exactly that. For a general workload orchestrator whose raw_exec driver runs on every system it supports, Nomad. jobscheduler’s own Mac VM backend is partly built and no job can ask for a VM yet (what is not built).

A job, and what bounds it

A job is one OCI image run to completion: the image pinned by digest, a command, resource needs and constraints, a wall limit, a network policy and declared ports. Its id is the client’s or minted by the service, at most 63 bytes, and a second submit of the same id with the same job answers from the job already made, so a retry after a lost answer runs nothing twice. A job is queued, placed, starting, running, and ends succeeded, failed, cancelled or lost, or fails to start with a code. Each state has a bound, so nothing depends on the client staying alive. A pool that sets neither waits at most 3600 s for a queued job, which then fails to start with no-capacity, and gives a placed job 900 s to start before it fails with start-timeout. A running job ends at its wall limit, on the agent’s own clock. A result is kept for 7 days by default, and its result keeps the last 8 KiB of each stream (design: Jobs and allocations).

An allocation is the scheduler’s private record that resources on one host are booked for one job. It is committed with the placement before the host is told, and it is freed only when the host confirms the container is gone or the provider says the host is absent. A host that is only silent frees nothing.

Placement

js-sched is the only placement. The server keeps one long-lived engine fed by each heartbeat’s load reading, applies the CPU slack setting (cpu_slack) and the pool’s memory_schedulable_percent, and places lease starts and queued jobs alike, whole-host jobs included (crates/js-sched, crates/js-sched-placer). A whole-host job marks the host with the least estimated time left; smaller jobs may use the host meanwhile only if they end inside that time (crates/js-whole). The estimates come from usage history only when the estimate feed is on, and it is off by default. Which offer a launch takes, and failover on capacity and quota refusals, are in js-sched and called by the scaler with the pool’s one machine provider; the walk over several providers in order is not built.

Machine providers

Every source of machines is one CapacityProvider (crates/js-elastic) with an idempotent acquire, a closed set of refusals, and an Unknown that never launches or frees. Its conformance suite runs against every provider: the registered hosts’ StaticCapacity, Lambda Labs, AWS EC2, GCP Compute Engine and the fake. Before any acquire the scaler applies a pool’s caps and brake and writes its record, and a machine’s first hello is checked against the offer it was launched from. The cloud providers run against the real clouds only in suites run by hand.

The agent and its runtimes

js-agent registers, heartbeats at the interval the server proposes (by default 5,000 ms), takes a start and a stop per job, and lists the jobs it holds and their results in each heartbeat until the server acknowledges them. A stop for a job it does not hold retires the id, so a start that arrives late does not run it; the agent remembers the newest 4,096 retired ids, and lists the newest 96 of them in each heartbeat until the server acknowledges them. On Linux it starts each job with crun through a supervisor of its own that outlives the agent, so a restarted agent adopts the jobs it finds, and a contained job runs as a non-root job user. Docker or Podman is a fallback whose jobs get no network. On macOS it runs a job’s darwin bundle, pulled by digest, as a pooled user under a Seatbelt profile. With a log sink the agent uploads a job’s output to an object store while it runs, and GetLogs reads it from any offset.

Correctness and failure handling

What the code does when a part fails, and how that is tested. The failures are the ones the problem starts from.

Failure model

  • A client disappears. Nothing it holds keeps work alive. A queued orphan ends at the queue wait with no-capacity, a running one at its wall limit, and its result waits out the retention window.
  • A client loses an answer. It submits again under the same job id and gets the job already made.
  • A host goes silent. After, by default, 15,000 ms of silence the server reads it lost, and a lost host takes no new work. Its jobs and allocations stay as they are: a start it received may have run before any heartbeat listed it, so a placed job is never requeued on silence, and a job that never started ends at the start timeout with its allocation kept until the host confirms. A static host that dies for good and is never removed keeps its jobs booked until an operator removes it; the design accepts that limit.
  • The server restarts. A restart ends no running job: the hosts keep running them and list them again on their next hello. Stored queue-wait and retention deadlines are raised to at least the boot plus 120 s, so an outage does not expire them.
  • A start is sent twice, or arrives after its stop. The agent runs a start of a job it holds once, and a retired id does not run.
  • A cloud loses an answer, refuses, throttles or preempts. An acquire is recorded before it is sent and is idempotent on its id; boot failures and denials trip the pool’s brake to plan-only until an operator resets it; a machine that is not the scheduler’s is never released.

The simulation cell

js-sim-cell runs the real lease server, its job service and its registry under a deterministic kernel beside many fake agents, with a virtual clock and one random source, both from the seed, so every run replays from its seed (docs/simulation.md). A determinism lint, cargo test -p xtask --test determinism, fails on a clock or random-source read in the crates a run links that its allow-list does not name. After every step the cell checks the step invariants, and at the end the end invariants. Among them: no-double-booking, at-most-one-launch, one-terminal-answer, bookings-match-agents, no-result-lost, whole-host-is-exclusive, drain-kills-nothing, one-allocation-per-job, freed-only-when-confirmed, no-start-without-allocation, instances-within-limits, only-own-machines-released and no-acquire-while-plan-only. Each invariant has a negative case, an agent or a history built to break it, that the invariant must fail (crates/js-sim-cell/tests/invariants.rs, crates/js-sim-cell/tests/broken_agent.rs).

The headline over jobs, the_headline_over_jobs, runs 40 jobs on 20 hosts while some agents are cut off and two are killed mid-job and replaced: every job reaches one terminal state, none is launched twice, nothing is double-booked and no allocation is left booked or releasing. It runs on every pull request. The nightly sweep (.github/workflows/sim-sweep.yml) runs the smoke family over seeds no night swept before, and prints a replay command for any seed that fails; it is a correctness check, and it records no measurement.

Other tests

  • Agent conformance. The suite of crates/js-conformance runs every scenario against the reference fake agent and against the real js-agent lifecycle (the_js_agent_passes_every_scenario), and refuses an agent that runs a repeated start twice (a_repeated_start_that_runs_twice_fails_start_is_idempotent) or forgets an unacknowledged result (forgetting_an_unacked_result_fails_unacked_result_is_resent). The job service has its own suite (the_reference_service_passes_every_scenario).
  • The job store. One suite of checks runs over the in-memory fake, SQLite and Postgres (crates/js-jobs/tests/sqlite_jobs.rs, crates/js-jobs/tests/postgres_jobs.rs; the_whole_suite_runs_in_one_pass).
  • Containment. The real-crun tests of js-contain run as root in units of their own (cargo xtask crun-tests), for example a_lease_cannot_read_a_sibling_leases_directory. On a Mac the two-run isolation test checks that a second run on the same user finds nothing the first left (a_second_run_on_the_same_uid_finds_nothing_the_first_left); it runs as root, by hand, not on each pull request.
  • Lints as tests in xtask. The layering test holds each crate to its layer and keeps every kbf crate out of the dependency graph (nothing_may_come_from_kbf_as_any_kind_of_dependency). The spawn-site test holds every program the agent starts to the spawner that disclaims the Mac privacy grants (every_job_spawn_path_uses_the_disclaiming_spawner). This report’s own check is cargo test -p xtask --test report.

Coverage. CI’s coverage job measures lines and branches with cargo llvm-cov and holds every crate to its line of coverage-baseline with crates/js-coverage: a crate fails when it misses more lines or branches than its line records, and also when it misses fewer, so the file keeps no slack.

What is not built yet

What is not built, plainly, each read against the code:

  • The job model is not the only model. The lease API, the js lease commands, the js-lease crate and the lease file remain; deleting them is step 30 of the design. The agent wire still carries the run and lease messages beside the per-job ones. kbf, the first client, still uses leases; moving it to jobs is work in the kbf repository.
  • Postgres holds part of the state. Jobs, allocations and usage history are SQLite files; the host book is the registry’s memory and the store’s bindings.
  • One provider per pool. The server runs the fixed static-then-registry order, not DefaultPlatform; the ordered walk over several machine providers and over platforms is not built; Kubernetes, Cloud Run and ECS are refused as not built. The agentless static pool is still served.
  • Estimates. The estimate feed is off by default and reads leases only; whether to turn it on is an open question of the design.
  • Macs. Staged inputs and declared ports are refused on a native run; no job can ask for a VM; the darwin binaries are not notarized; the isolation test runs by hand.
  • Operations. One active server with no standby; a liveness route (/healthz) and no readiness route; no deny list of hosts; no supervisor definition (unit, manifest or chart) in the repository; no safe restore verb; one client token for the lease routes.
  • Not in v1 by design: reservations of capacity or of a whole host for a time (design: Non-goals).

The design’s plan for the rest is its list of steps (design: From today’s code to the design).
