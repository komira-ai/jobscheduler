Install

The lease server, the js client and the agent are Rust binaries built by the repository's release workflow. There is no package repository, no container image and no installer. The Linux binaries are static (musl, x86_64); the macOS ones are for Apple silicon and are not codesigned or notarized. There is no lease server for macOS.

The agent's Debian package is not published. The repository builds it with nfpm, checks what it contains and attests it, as a workflow artifact kept for seven days. That workflow publishes no release, no package repository and no registry. A host gets the agent from the release archive and the unit in packaging/js-agent, as the steps below say.

  1. Take the archives works today

    Every push to main that changes code that ships is released as the next version, after the checks of ci other than the macOS job have passed. A release for version X.Y.Z carries:

    ArchiveHolds
    js-lease-server-X.Y.Z-x86_64-unknown-linux-musl.tar.gzthe lease server
    js-X.Y.Z-x86_64-unknown-linux-musl.tar.gz, js-X.Y.Z-aarch64-apple-darwin.tar.gzthe js client
    js-agent-X.Y.Z-x86_64-unknown-linux-musl.tar.gz, js-agent-X.Y.Z-aarch64-apple-darwin.tar.gzthe agent
    js-bundle-X.Y.Z-... for both targetsthe tool that packs, prints and verifies darwin bundles
    js-mac-session-X.Y.Z-aarch64-apple-darwin.tar.gz, js-mac-provision-X.Y.Z-aarch64-apple-darwin.tar.gzthe root helper and the pf anchor installer a Mac node installs
    SHA256SUMSthe SHA-256 of the nine archives

    Each archive unpacks to a directory named like the archive without .tar.gz, and holds the binary and LICENSE.

  2. Verify them works today

    This needs the GitHub CLI (gh), signed in. The checksum proves the download is intact; the attestation proves the file was built from this repository by the release workflow, from main, at the commit the tag names.

    $ gh release download vX.Y.Z -R komira-ai/jobscheduler -p 'js-lease-server-*-x86_64-unknown-linux-musl.tar.gz' -p SHA256SUMS
$ sha256sum -c --ignore-missing SHA256SUMS
$ gh attestation verify js-lease-server-X.Y.Z-x86_64-unknown-linux-musl.tar.gz -R komira-ai/jobscheduler \
    --signer-workflow komira-ai/jobscheduler/.github/workflows/release.yml \
    --source-ref refs/heads/main \
    --source-digest "$(git rev-parse vX.Y.Z^{commit})"

    For the client use -p 'js-[0-9]*-x86_64-unknown-linux-musl.tar.gz', and for the agent -p 'js-agent-*-x86_64-unknown-linux-musl.tar.gz'.

    From docs/release.md, "Downloading and verifying". git rev-parse needs a clone with the tags.

  3. Start the lease server works today

    The server needs a token for clients (a regular file owned by the server's user, mode 0600 or 0400, one token of printable ASCII, at least 32 bytes), a state file, and a pool file for the agents that will join. The paths below are examples. The first start says --boot initialise, which may create the state file; every later start says --boot resume, which refuses a missing one.

    # agent-pool.toml: the pool the agents join
name = "hosts"
class = "whole-node"
max_machines = 4
[shape]
cpu_millis = 8000
memory_bytes = 17179869184
    $ js-lease-server --listen 127.0.0.1:7300 --state-file /var/lib/jobscheduler/leases.toml --boot initialise \
    --token-file /etc/jobscheduler/client-token \
    --agent-pool-config /etc/jobscheduler/agent-pool.toml \
    --agent-token-file /etc/jobscheduler/join-tokens

    The pool's join tokens are in the file after --agent-token-file, one per line, each as strong as the client token, in an owner-only file. The default listen address is 127.0.0.1:7300; off the loopback the server needs both --tls-cert and --tls-key and refuses to start without them. A start the server refuses prints the flag at fault and exits with status 2.

    There is one client token and so one trust domain: share it only with parties that trust each other with every host of the pool.

    From the module documentation of crates/js-lease-server/src/lib.rs (the flags table and "Who may do what") and crates/js-lease-server/src/agent_pool.rs (the keys of the pool file). The server's flag reference is that documentation; the repository has no page that renders it.

  4. Install the agent on a Linux host works today

    The agent runs as root, with a rootful Docker or Podman beside it, and refuses to start under ProtectSystem=, PrivateMounts= or PrivatePIDs=. The unit runs /usr/bin/js-agent and reads /usr/lib/tmpfiles.d/js-agent.conf. Put the binary at the first path, js-agent.service in /usr/lib/systemd/system and tmpfiles.conf from packaging/js-agent at the second, where the Debian package puts them. Then, as root:

    1. make the directories: systemd-tmpfiles --create /usr/lib/tmpfiles.d/js-agent.conf;
    2. write the pool's join token to /etc/js-agent/token, mode 0600;
    3. mount a disk of its own at /var/lib/js-agent/scratch (the agent refuses a state root on the same disk as the scratch root);
    4. systemctl edit js-agent: clear ExecStart= and set the whole line again with this host's --server and --pool (the shipped --server is a placeholder the agent refuses);
    5. systemctl enable --now js-agent.

    A missing mount fails silently. With the mount of step 3 absent, step 5 exits 0 and starts nothing; systemctl status js-agent shows the unmet ConditionPathIsMountPoint.

    The agent reads no environment variable and no configuration file: its flags are the ExecStart line. It exits 2 for a wrong flag or file, a job engine it cannot use, or a server that refuses the host for good, and the unit restarts it every 30 seconds, so a refusal is read from the journal. --server is https://host:port; http:// is accepted only for localhost, 127.0.0.0/8 and ::1. The unit's --runtime docker runs jobs through the engine at --container-bin. A second unit, js-agent-crun.service, runs jobs with crun on a farm node; packaging/js-agent/crun_host_setup.sh sets a host up for it and installs it, and the unit is not enabled or started.

    From packaging/js-agent/js-agent.service (its header), packaging/js-agent/nfpm.yaml, .github/workflows/js-agent-deb.yml (its header), packaging/js-agent/crun_host_setup.sh (its header) and the flags table of crates/js-agent/src/lib.rs.

  5. Lease a host works today

    With the agent heard by the server, a client leases the host:

    $ js --server http://127.0.0.1:7300 --token-file ~/.js-token lease acquire --class whole-node --max-wall 2h
$ js --server http://127.0.0.1:7300 --token-file ~/.js-token lease list

    acquire prints lease <id> host <host> expires <ms>. A whole-node lease is answered pending until the host's agent reports it ready, and the client looks at the list every two seconds for at most --wait-pending, 60 seconds by default, then releases a lease that is still pending. The token file is a regular file owned by you, mode 0600 or 0400.

    From the module documentation of crates/js-cli/src/lib.rs.

What is not shipped

  • none A published package or container image of the agent, the lease server or the client.
  • none A lease server for macOS.
  • not proven That the macOS archives come out byte-identical when a partly published release is re-run.
  • not available yet The agent flag --allow-host-jobs: it is refused at start.

Sources: docs/release.md ("What is released" and the note on the macOS archives) and the flags table of crates/js-agent/src/lib.rs.
