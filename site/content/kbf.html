kbf on jobscheduler

kbf is the first user of jobscheduler and the repository it was lifted out of. This page separates three things: what kbf takes from this repository today, what the documents say kbf does with it, and the design for running kbf's actions on the agent, which is not built.

About the kbf facts. The statements about kbf below are the repository's own documents, written against a kbf revision those documents name. This repository does not contain kbf, and kbf may have moved since. Check kbf's tree before you rely on a statement about it.

What kbf takes from this repository

The code here was written for kbf and lifted out of it. The first user depends on these crates by git revision: it names every js-* crate once, in its root [workspace.dependencies], all at the same revision of this repository, and a bump is a deliberate pull request there that runs its full CI. Where a crate moved, kbf keeps its name as a shim that re-exports the crate here. This repository never depends on kbf: a test refuses a kbf-* dependency, and deny.toml bans kbf's crates by name.

The pieces a scheduler server is built from are here:

  • js-sched, the pure scheduler core, including admission by load (see placement);
  • js-server-core, the loop around it that carries its effects out: a record is committed before anything that depends on it happens, and several frontends may share one store;
  • js-sizing, the estimator that predicts an action's CPU and memory from earlier runs;
  • js-agent, which the design documents call the generic half of the kbf daemon.

Sources: docs/layering.md ("Depending on the crates by git revision" and "Moving a crate in from another repository"), the module documentation of crates/js-server-core/src/lib.rs and crates/js-sizing/src/lib.rs, and docs/design.md, decisions 1 and 2 of the summary.

What kbf runs today

According to docs/design/kbf-today.md, checked against the kbf revision it names, kbf has two scheduler cores selected by --scheduler-core, and only the legacy one is built into a running server; js is refused at start unless a test-only feature is built. The same document says that nothing in kbf runs js-agent, and that no lease client of jobscheduler was in use.

The design for kbf on the agent

docs/design/kbf-on-js-agent.md is marked "design only": nothing in it is built or approved to run. It proposes the following, and the right-hand column is the state of each part in this repository.

ProposalState
A lease server is deployed; kbf leases whole hosts from itthe lease API exists kbf's client: not built
kbf submits each action as a run on its lease, through POST, GET and DELETE on /v1/leases/{id}/runsthe interim run API exists runs are in memory only: a restart forgets them
js-agent stands alone on every host, with no kbf process beside itthe agent is standalone kbf on it: design only
Each action runs in its own digest-pinned image; the agent returns the container's exit codedesign only
The task writes its outputs with one presigned upload, and kbf's frontend verifies what it reads backdesign only
A kbf flag, --executor, chooses between the agent and kbf's own daemon, as the way backdesign only

The document keeps jobscheduler generic: kbf's own types stay in kbf, and jobscheduler gets only generic fields.
