Concepts

A job is recorded, then placed

A client calls the job service, which the server serves on a port of its own, --job-listen. SubmitJob checks the job, admits it when a host, or a machine provider of the pool, could ever serve it, and records it as queued before it answers; it never waits for placement. A job that nothing could serve is refused no-capable-host, and nothing is recorded. The job service and host routes need the client's bearer token. /healthz needs none, and neither do /v1/pools and /status, which are served only when the server listens on a private address, and only to a private peer. An agent's routes take a join token instead.

A job has a wall limit, and the server refuses a job without one: a limit that is absent or 0 is refused wall-time-not-positive, and one above the server's --max-job-wall is refused wall-time-above-ceiling. A cancel of a queued job ends it at once. A cancel of a job that is placed, starting or running records the intent to cancel, and the job is shown in its state with the intent. A job that has ended is kept, with its result, for --job-retention, seven days unless the server is told otherwise.

# the shapes of the js client's commands
js job submit [--id ID] --spec.image REF [--spec.args A ...] [--spec.env K=V ...]
js job get --job-id ID
js job cancel --job-id ID
js job list [--states S ...] [--labels K=V ...]

A submit that is repeated needs its id. The same id with the same job answers from the job the first submit made. Without --id, js draws an id and prints it on stderr before it sends. When the request was sent and no answer was read, the job may exist: js says so and exits 9, and the same command with the same --id is safe to run again.

The server is single-tenant: there is one client token, and so one trust domain. Whoever holds it can list every host and read every pool, and reset a pool's brake. The job service has its own clients and roles. A client of the role client reads and cancels only its own jobs, and an operator every job. The token of --token-file is the client default, an operator, and --client-token adds another.

Hosts and pools

Capacity comes in pools. A pool has a name, a class, a shape and max_machines. The shape is what the pool books for every host: cpu_millis and memory_bytes, and optionally gpus, gpu_class and disk_bytes. Hosts reach a pool in these ways:

  • A static pool: the operator lists the hosts in a file. A job runs on no host of that file: only the hosts that register take jobs.
  • Agents that join: an agent says hello with a join token, offers its CPU, memory and GPUs, and heartbeats. The pool file for them is --agent-pool-config.
  • An elastic pool: a provider launches machines for requests that wait. The provider kinds compiled in are static and lambdalabs. A pool's launch is plan, which launches nothing, unless the file says live; a live pool also has caps on instances and on spend per hour and per day, and a brake: three launch or boot failures in a row trip it back to plan, and only an operator's reset clears the trip.

memory_schedulable_percent is a whole number from 1 to 100, 100 by default. A pool books that share of each host's memory, rounded down.

A pool file names a class. The shipped classes are whole-node and gpu-host, which stays as an alias; any other name is a class that books a whole host too. not built A class that books only part of a host (a mixed pool) cannot be served: the server refuses the pool file with "a mixed pool (a class that books part of a host) is not served by this server yet".

A whole node: exclusive, quiet, reserved, capped

A job that needs the whole host is a request of its own, not a large one. It promises four things that a big share does not:

  1. Exclusive. It books every dimension of the host (CPU, memory, disk, all GPUs, all VM slots), and nothing else is placed on the host until it is released.
  2. Quiet. Before the client can use it the host has no run, no VM and no leftover of an earlier job, the post-job checks are clean and the host is not tainted.
  3. Reserved. A queued request is given exactly one host, by draining it, so a stream of small requests cannot starve it. The engine queues each queued job that needs the whole host as a whole-machine request, and marks the host it is to have.
  4. Capped. Pool limits bound how many hosts are reserved or held whole.

Which host a reservation drains is decided by the drain cost: the host's tail, the latest end of its leases, each ending at its estimate cut to its max-wall bound, or at the bound when it has no estimate; then the fewest leases, then the lowest host id. A job that needs the whole host stays placed while its host's agent prepares the host, and moves to starting when the agent reports it ready. A prepare that is not ready by the pool's prepare_timeout, ten minutes unless the pool file sets it, fails, and the job goes back to queued; after max_replace failed prepares it fails to start with exclusive-not-ready.

A dedicated pool (class whole-node) lets every host be whole. The pool file's whole-node keys are max_whole_node, max_draining, max_whole_node_per_consumer, keep_for_ordinary, allow_last_capable, drain_after, drain_deadline, reserve_backoff, max_reserve_attempts, prepare_timeout, max_replace and regain_grace; gpu-host books a whole host without them and refuses them.

Placement by CPU and memory

The placement core is js-sched, a pure state machine: it takes time as an input and reads no clock. It admits an action to a worker when what the worker's readings measure, plus the predicted cost of the leases no reading covers yet, plus the predicted cost of the new lease, stays within the worker's CPU and its memory, each charged at a cost the lease keeps from its grant to its result. The defaults plan a worker to 1.1 times its CPU (--placement-cpu-slack) and 1.0 times its memory. A worker with no usable reading is charged by predicted cost alone.

The cost comes from earlier runs of similar actions (js-sizing):

ResourceEstimate
Memoryround_up_256MiB(max(1.2 * M + 128 MiB, held, oom_floor)), where M is the largest uncensored sample of the last 256 or more runs, and at least 1 GiB
CPUround_up_250m(P90(cpu_usage / wall)), clamped to 250 m and the node's cores; 2000 m for a key with no CPU sample

A booking at or above the memory of the largest matching live node owns the host: the estimate never reaches a whole host, and the caller books cold instead.

Where it stops. js-lease-server places every job with js-sched, the only placement; --placement is deprecated and does nothing. The server keeps one scheduler for its life, told of every hello, accepted heartbeat (with its load reading) and stop. A pass over the queue on each tick walks the queued jobs in order, one placement round of the scheduler per job, over the hosts that could take a job now. A host's free capacity is what its shape leaves after the job allocations on it. Mode off of the load rule is a rollback switch to the booked rule, and not a supported mode.

Sources: the module documentation of crates/js-sched/src/lib.rs (admission by load), crates/js-sched/src/admission/config.rs (the slack), crates/js-sizing/src/lib.rs (the estimates) and crates/js-sizing/src/summary.rs (COLD_CPU_MILLIS), crates/js-sched-placer/src/place.rs and the --placement row of the flags table of crates/js-lease-server/src/lib.rs (what the server calls), docs/design/placement-by-load.md (the leases charged flat).

A silent host

A host that goes silent for good and is never read absent keeps its jobs as they are, with their allocations booked. A job becomes lost in two ways: the provider reads its host absent, or the host comes back and does not list the job.
