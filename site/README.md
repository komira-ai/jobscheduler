# site: the jobscheduler.dev website

The same stack as kbf.dev, mopm.dev and tierstore.dev: plain TypeScript compiled by `tsc`, a build program (`tools/`)
that prerenders the pages, no framework, no bundler, no runtime dependencies. `package.json` lists two development
packages, pinned exactly; Node is the exact version in `.node-version`.

```sh
npm ci --ignore-scripts --no-audit --no-fund
npm run typecheck
npm test            # compiles, then runs test/*.test.ts
npm run build       # writes dist/
npm run golden      # after a change meant to alter a page or an asset: rewrites test/golden.manifest
```

`test/golden.manifest` is generated by `npm run golden` and committed. It is empty in the commit that adds the site,
because that commit was written without running Node: the golden test fails, and says so, until the manifest is
generated and committed.

## Where it lives and why

The site is `site/` at the root of the repository, next to `docs/`, `packaging/` and `crates/`. It is not a crate (the
workspace is Rust and the site's tooling is Node), it ships in no release (a file ships only when it is in a crate of a
released binary or a root build input, `docs/release.md`), and it reads the documents and sources its pages rest on
from the checkout it is in. The tests find the repository root by looking for `.github/workflows` above them
(`test/support.ts`), so moving the directory changes no code; `.github/workflows/jobscheduler-site.yml` names the
directory in its `paths:` filters, `working-directory` and `node-version-file`, and `test/supply-chain.test.ts` checks
that the workflow and the site agree.

| Path | What |
|---|---|
| `content/*.html` | the page copy: the inside of each page's `<main>`. Each claim comes from the code or a document of this repository, and a page says where (a `source-note` paragraph); what is not built is marked as such |
| `served-policy.ts` | the Content-Security-Policy the site is to be served under, a copy of the one the sibling sites are served under (`infra/site/lib/site-stack.ts` in komira-ai/kbf); a change there is made here in the same step |
| `static/theme.css` | the shared theme (kbf.dev, mopm.dev, ucdk.dev, tierstore.dev), copied byte for byte; `test/theme.test.ts` pins its sha256. Never edited here: a change to the theme is made once, upstream, and the new file and digest are taken by every site that shares it |
| `static/site.css` | this site's own rules, loaded after the theme |
| `src/copy.ts` | copy buttons on command blocks |
| `tools/` | `pages.ts` (routes, titles, navigation), `layout.ts` (the page shell, with the `> jobscheduler` mark), `build.ts`, `check-dist.ts` (the rules the policy would enforce in a browser), `links.ts`, `csp.ts`, `manifest.ts` |
| `test/` | golden output (`golden.test.ts`), links, Content-Security-Policy, theme digest, the public-repo scan (`hygiene.test.ts`), the supply-chain policy of the site's own packages and workflow, and the statements of the pages held to the source (`claims.test.ts`) |

## The statements are held to the source

`test/claims.test.ts` pairs a phrase of a page with the phrase of a source file it rests on (a crate's module
documentation, a document under `docs/`, a unit file, the release document). When the source changes, the test fails
and names the page and the phrase to revisit; when a page is reworded, it fails until its row follows. It also checks the
pool-file keys the install page shows against the keys the server reads, the archive names against `docs/release.md`,
and that every file a source note names exists.

The pages about kbf repeat what `docs/design/kbf-today.md` and `docs/design/kbf-on-js-agent.md` say, with the revision
caveat those documents carry; the site does not claim anything about kbf's tree that those documents do not.

## No publish workflow

Nothing here deploys the site. The domain, the bucket and the publishing job are a separate step; until then the
workflow builds and tests on pull requests and on pushes to `main`, and that is all.
